# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A Spring Boot 3 (Java 21) REST application (`org.bee`, artifact `SBProjects`) that demonstrates several backend patterns in isolated modules: `@ConfigurationProperties` binding, async notification processing, JSON Schema-validated event ingestion, Resilience4j circuit breaking/retry, MapStruct mapping, and Spring Data JPA — see `../README.md` for the full endpoint table and sample `curl` requests.

## Banking module rules

Path-scoped guidance for the banking module lives in `.claude/rules/banking/` and loads when working on matching files: `architecture.md` (layers, dependency rules, invariants), `design.md` (domain/entity/request/mapping), `code-style.md`, `controller-layer.md`, `service-layer.md`, `repository-layer.md`, `gateway-layer.md`, `bff-layer.md` (portal BFF/orchestration), `exceptions-and-messages.md`, `testing.md`, `security.md`, `api-design.md` (incl. OpenAPI sync). Read the relevant file before changing that layer.

## Commands

```bash
mvn clean compile          # compile
mvn test                   # run all tests + generate a JaCoCo coverage report
mvn test -Dtest=ClassName                         # run a single test class
mvn test -Dtest=ClassName#methodName              # run a single test method
mvn spring-boot:run        # start the server (port 8081, context path /brite)
```

`mvn test` also runs the `jacoco-maven-plugin` (`prepare-agent` + `report`, version managed by `spring-boot-starter-parent`), producing `target/site/jacoco/index.html` (plus `jacoco.csv`/`jacoco.xml`) — open the HTML file directly in a browser, no server needed. It's build output under `target/`, so it's git-ignored and regenerated on every test run.

**A live MySQL instance is required to run the app or most of the test suite.** The datasource in `../src/main/resources/application.yml` (`spring.datasource.url: jdbc:mysql://localhost:3306/db_example`) is real — there is no H2/test profile override for the app itself (`src/test/resources` doesn't exist), so `@SpringBootTest` classes boot the full context against that same MySQL instance. `spring.jpa.hibernate.ddl-auto: update` auto-creates/updates tables (`events`, `accounts`, `customers`, `account_transactions`, `withdrawal_history`, `bank_locations`, `bank_location_services`) on startup. The one exception is `AccountRepositoryTest`, a `@DataJpaTest` that swaps in embedded H2 (already a dependency) instead — see Testing below.

Base URL for every endpoint: `http://localhost:8081/brite` (context path `/brite` is configured in `application.yml`). Interactive API docs for the banking module: `http://localhost:8081/brite/swagger-ui/index.html` (see "Banking OpenAPI spec" below). If 8081 is already taken (e.g. an IDE-launched instance), run a second copy with `mvn spring-boot:run -Dspring-boot.run.arguments=--server.port=8082` rather than killing the other one.

## Architecture

### Module layout

Each top-level package under `org.bee` is a self-contained vertical slice (controller → service → repository), independently scanned via `scanBasePackages`/`@ConfigurationPropertiesScan` in `SpringBootProjectsApplication`:

- `org.bee.banking` — client/account registration, withdraw/deposit, bank statements, async notifications, Resilience4j payment demo, a `Filter`-based API gateway (`org.bee.banking.gateway`: btid tracing, per-customer rate limiting, request-body logging) fronting the whole module, a hand-written OpenAPI spec + Swagger UI (`src/main/resources/static/openapi`, `static/swagger-ui`), account suspension (`AccountSuspensionService`, suspend/update/reactivate endpoints, a scheduled expiry job) and paginated/single account-status lookup (`AccountStatusStatementService` in `org.bee.banking.service`, view DTO in `org.bee.banking.domain`), and a real JPA data model (`org.bee.banking.entity` + `org.bee.banking.repository.jpa`) persisted to MySQL — see "JPA-backed persistence" below
  - **BFF for the banking UI portal**: `org.bee.banking.bff` (`/bff/v1/portal/*`: `home`, `accounts/{n}/overview`, `accounts/open`) composes the banking services in process into screen-shaped DTOs; tunables in `banking.portal.*`, CORS via `PortalCorsConfig`. See `.claude/rules/banking/bff-layer.md`.
- `org.bee.retail` — in-memory product catalog
- `org.bee.events` — JSON Schema-validated event ingestion, persisted via JPA
- `org.bee.configs` — `@ConfigurationProperties` classes (`BriteEmailConfigValues`, `BriteSmsNotificationConfigValues`, `BriteApplicationConfigValues`) plus a read-only controller that echoes them back
- `org.bee.restapi.versioning` — API-versioning strategy demos (URI/param/header/content-negotiation)
- `org.bee.sample` — a small standalone lookup demo, unrelated to the other modules
- `org.bee.common` — cross-cutting concerns that apply app-wide rather than to one module (currently just `org.bee.common.logging.ExecutionTimeLoggingAspect`); explicitly added to `scanBasePackages` in `SpringBootProjectsApplication` since it's outside the modules listed above

### Mixed persistence: banking and events are JPA/MySQL, retail is still in-memory

The **events** module persists via `EventEntity`/`EventRepository extends JpaRepository`, and (as of the banking JPA migration) so does the whole **banking** module — real accounts, customers, transactions, and withdrawal history rows in MySQL that survive app restarts. Only **retail** is still purely in-memory:

- `ProductRepository` (retail) — backed by a **`private static Map`** populated once from `LoadProductData.loadproddata()`. Because it's static, mutations from one test (e.g. `addproduct` in a test method) persist for the JVM's lifetime and leak across test methods/classes — be careful writing tests that assert exact catalog size or contents.

### JPA-backed persistence for banking (entities, repositories, and the domain-object mapping seam)

Banking used to be a `ConcurrentHashMap`-backed mock store; it's now backed by real JPA entities. The **domain objects** (`Account`, `Customer`, `Address`, `AccountTransaction`, `WithdrawalForm` in `org.bee.banking.domain`) that the service/controller layers use are unchanged, so `ClientAccountService`, `BankStatementService`, `AccountStatusStatementService`, and every controller/DTO needed **zero changes** for this migration — all the mapping happens inside the repository classes:

- **Entities** (`org.bee.banking.entity`): `AccountEntity` (one row per real account — see below), `CustomerEntity`, `AddressEmbeddable` (`@Embeddable`, inlined into `CustomerEntity`/`WithdrawalHistoryEntity`, no separate table), `AccountTransactionEntity`, `WithdrawalHistoryEntity`.
- **Raw Spring Data repositories** (`org.bee.banking.repository.jpa`): `AccountJpaRepository` (extends `JpaRepository` + `JpaSpecificationExecutor` for dynamic filtering), `CustomerJpaRepository`, `AccountTransactionJpaRepository`, `WithdrawalHistoryJpaRepository`. Application code never touches these directly.
- **Facade repositories** (`org.bee.banking.repository`, same package/class names as before the migration): `AccountRepository`, `TransactionRepository`, `WithdrawalRepository` now wrap the JPA repositories above, mapping entity ↔ domain object internally (`AccountRepository.toDomain`/`toEntity` etc.) so their **public method signatures are unchanged** (`findByAccountNumber`, `search`, `save`, `withdraw`, `deposit`, `closeAccount` on `AccountRepository`; `recordTransaction`/`findByAccountNumber` on `TransactionRepository`; `createWithdrawal` on `WithdrawalRepository`). This is why `ClientAccountServiceTest`/`AccountStatusStatementServiceTest`, which mock these facade classes, didn't need to change at all — they never cared about the in-memory-vs-JPA implementation detail.

**Bank locations** (`BankLocationEntity` + `BankAddressEmbeddable` → `bank_locations`, with the `Set<BankOperationServices>` as an `@ElementCollection` in `bank_location_services`; domain shapes `BankLocations`/`BankAddress`/`LocationType`/`BankOperationServices` in `org.bee.banking.domain`) model branch offices and ATMs. `LocationType` is `OFFICE`/`ATM`/`BOTH`; `opensAt`/`closesAt`/`phoneNumber` are the *office's* and are null for `ATM`. Hours are 08:00-16:00 wall-clock in `timeZone` `America/Chicago` (not the literal "CST", so daylight saving is handled). `BankLocationDataSeeder` seeds 20 locations when the table is empty (same run-once rule as `AccountDataSeeder`; `BankLocationDataSeederTest` runs it against H2). `GET /v1/api/locations` (`BankLocationController` → `LocationBasedOperationService` → `LocationBasedOperationRepository`, the facade over `BankLocationJpaRepository` that maps entity → `BankLocations`) is a `Specification` search like the account one: optional `type`/`city`/`state`/`zip`/`service` filters plus `Pageable` (default `size=20`, `sort=name`; valid sort keys `name`, `locationType`, `city`, `state` — city/state are remapped to the embedded `address.*` paths, checked before the query so a bad one is a `400`). **`type` matches by capability, not stored value**: `OFFICE` → `OFFICE`+`BOTH`, `ATM` → `ATM`+`BOTH`, `BOTH` → `BOTH` only. It isn't cached. `GET /v1/api/locations/{id}` (`LocationBasedOperationService.getLocation`) returns one location or throws `LocationNotFoundException`, which `BankingExceptionHandler` maps to a plain-text `404` — unlike accounts, this one-record path-variable endpoint does exist, since locations have a stable numeric id (both the list and `/*` patterns are in `BANKING_URL_PATTERNS`). `BankATMLocations` is still an empty placeholder class.

**`AccountEntity` is one row per real account (checking OR savings), not one row per customer pairing.** The `Account` *domain* object conflates a checking and a savings account into one object with a pair of nullable fields (`checkingAccountNumber`/`checkingBalance` and `savingAccountNumber`/`savingBalance`) — that shape only ever made sense for the old map keyed by account number; a relational table models "one account number = one row" directly. `AccountRepository.toDomain(AccountEntity)` picks the checking-or-saving field pair to populate based on `entity.getAccountType()`. If you add a new field to `Account` that should persist, add it to `AccountEntity` (or `CustomerEntity`/`AddressEmbeddable` if it's a person/address field) and to both mapper directions in `AccountRepository`.

**Account numbers are generated from `accountJpaRepository.count() + 10001`**, zero-padded to 10 digits (`AccountRepository.save()`) — same scheme and starting point as the old in-memory counter, so existing seeded/documented account numbers stay valid across the migration. `AccountDataSeeder` (`@PostConstruct` on a `@Component`, not the `AccountRepository` constructor anymore) seeds the same 52 demo accounts **only if the accounts table is empty** — real MySQL persists across restarts, so unconditional reseeding (the old constructor's behavior) would create duplicates every time the app starts. If you see "Accounts table already has data; skipping demo seed" in the logs, that's expected on any restart after the first.

**Optimistic locking (`@Version` on `AccountEntity`)** replaces the old `ConcurrentHashMap.computeIfPresent`'s atomicity guarantee for `withdraw`/`deposit`/`closeAccount`: two concurrent writes to the same account row now fail one of them with an `ObjectOptimisticLockingFailureException` instead of silently losing an update. There's no retry-on-conflict logic; a concurrent-write test would need to assert the exception, not a specific final balance.

### Account number prefix drives account type resolution

Account numbers are the source of truth for account type, not a stored field on the `Account` *domain* object: `ClientAccountService.withdrawAndSaveToAccount`/`depositAndSaveToAccount` read the first two characters of the account number (`"CH"` → `CHECKING`, `"SV"` → `SAVINGS`) and reject anything else with `UNRECOGNIZED_ACCOUNT_PREFIX`. (`AccountEntity` *does* have its own `accountType` column, set at creation time - the prefix-parsing is purely a service-layer convenience for withdraw/deposit requests, not a re-derivation of unknown data.) Any code that generates or accepts account numbers (e.g. `AccountRepository.save()`) must keep producing `CH-`/`SV-`-prefixed IDs, or withdraw/deposit will fail for those accounts even though registration succeeds. The numeric part after the prefix is always zero-padded to at least 10 digits (e.g. `CH-0000088291`, `SV-0000020004`) — both `AccountDataSeeder`'s seed data and `AccountRepository.save()`'s dynamic generator (`String.format("%010d", ...)`) follow this; keep it that way if you add more seed accounts or change the generator.

### Account status (ACTIVE/SUSPENDED/CLOSED) gates withdraw/deposit

`Account` carries `accountStatus` (`AccountStatus.ACTIVE`/`SUSPENDED`/`CLOSED`), `createdDate`, `closedDate`, and the suspension fields (see "Account suspension" below). `AccountRepository.save()` defaults new accounts to `ACTIVE` with `createdDate = today` if not already set. `withdraw()`/`deposit()` throw `AccountClosedException` (mapped to `400` by `BankingExceptionHandler`) if the account is `CLOSED`, and `AccountSuspendedException` (`400`) if it is `SUSPENDED` — both checks run *before* the balance/minimum-balance checks. `POST /v1/api/accounts/{accountNumber}/close` (`ClientAccountController.closeAccount` → `ClientAccountService.closeAccount` → `AccountRepository.closeAccount`) transitions `ACTIVE` or `SUSPENDED` → `CLOSED`, stamps `closedDate` and clears any suspension; it throws `AccountClosedException` (`400`) if already closed, `AccountNotFoundException` (`404`) if the account doesn't exist. There's no reopen path for a `CLOSED` account (suspension is the reversible state). `AccountDataSeeder` seeds 52 accounts total (26 checking, 26 savings) on first startup against an empty database, including two pre-closed accounts (`CH-0000010004`, `SV-0000020004`) for demoing the closed state; everything else seeds `ACTIVE`. `AccountStatusDemoSeeder` adds 40 more (92 total): 20 `CLOSED` and 20 `SUSPENDED` — see below.

`POST /v1/api/accounts/close` is the bulk counterpart (`ClientAccountController.closeAccounts` → `ClientAccountService.closeAccounts`, body: `BulkCloseAccountsRequest{accountNumbers: List<String>}`, `@NotEmpty`-validated → `400` if empty). It's deliberately best-effort, not all-or-nothing: it loops calling `accountRepository.closeAccount(...)` **directly**, not `this.closeAccount(...)` — a self-invocation within the same Spring bean would bypass that method's own `@CacheEvict` proxy, so calling the repository straight avoids the classic Spring-AOP self-invocation pitfall. Catches `AccountNotFoundException`/`AccountClosedException` per account and routes them into `BulkCloseAccountsResult.failures` (`{accountNumber, reason}`) instead of aborting the batch; successes go into `closedAccounts`. Returns `200` always (per-item outcomes are in the body, not the HTTP status) and evicts the account-search cache once for the whole batch rather than once per account.

### Account suspension (SUSPENDED state, `AccountSuspensionService`)

`SUSPENDED` is a reversible block: **a suspended account rejects every withdraw and deposit until it is ACTIVE again.** State lives on `AccountEntity`/`Account`: `accountStatus = SUSPENDED`, `suspended` (boolean flag, true exactly while suspended), `suspendedStart`/`suspendedEnd` (`LocalDateTime`; end null = indefinite) and `suspensionNotes` (≤500 chars). The facade always writes status + flag together and treats *either* as "suspended" (`AccountRepository.isSuspended`).

- **Endpoints** (`ClientAccountController` → `AccountSuspensionService` → `AccountRepository`): `POST /v1/api/accounts/{n}/suspend` (body `SuspendAccountRequest{notes (required), startDateTime?, endDateTime?}`), `PATCH /v1/api/accounts/{n}/suspension` (`UpdateSuspensionRequest{notes?, endDateTime?}`, at least one), `POST /v1/api/accounts/{n}/reactivate`. All return the `Account`. There is deliberately no `GET .../suspension`; read suspension data from `GET /v1/api/accounts?accountNumber=` / `?status=SUSPENDED` (`AccountStatusView` carries the four fields).
- **Rules split**: time-window rules are in the service (start defaults to now and can't be future; end must be after start *and* in the future; update needs ≥1 field and a future end) and throw `IllegalArgumentException` (`400`); state rules are in the facade (closed → `AccountClosedException`, already suspended → `AccountSuspendedException`, update/reactivate when not suspended → `IllegalArgumentException`, new end must be after the *stored* start). `AccountSuspendedException` → `400` plain text.
- **Lifecycle**: suspend `ACTIVE`→`SUSPENDED`; reactivate `SUSPENDED`→`ACTIVE` and **clears** flag/start/end/notes (no history is kept); close from `SUSPENDED` is allowed and clears them too.
- **Auto-expiry**: `AccountSuspensionExpiryJob` (`@Scheduled`, `@EnableScheduling` is on `SpringBootProjectsApplication`; `banking.suspension.expiry-job.enabled`/`interval-ms`, default 60 s) calls `AccountSuspensionService.reactivateExpiredSuspensions()` → `AccountRepository.reactivateExpiredSuspensions(now)`. Until a run happens an expired suspension still blocks, so the lag is ≤ one interval. Call it through the service bean, not `this`, so `@CacheEvict` applies.
- **Cache**: all four service mutations carry `@CacheEvict(ACCOUNT_SEARCH_CACHE, allEntries = true)` because `AccountStatusView` shows status + the suspension fields.
- **BFF**: `AccountOverviewResponse` exposes `suspended` and `suspendedUntil` (not the notes).
- **Seed data**: `AccountStatusDemoSeeder` (idempotent *per account number*, not "if empty", so an existing DB with the 52 base accounts still gets the 40; it injects `AccountDataSeeder` purely to force init order) seeds 20 CLOSED (`CH-0000030001..30010`, `SV-0000040001..40010`, created 26–40 months ago, so outside the default 18-month window: use `months=48`) and 20 SUSPENDED (`CH-0000050001..50010`, `SV-0000060001..60010`, created 4–14 months ago; 14 end 3–60 days ahead, 6 indefinite, none pre-expired so the job leaves them alone). Seed dates stay relative (`LocalDate.now().minusMonths(n)` / `LocalDateTime.now()`). Mirror: `db/data/05_seed_closed_and_suspended_accounts.sql`.
- **Database migration gotcha**: `ddl-auto: update` adds the new columns but **never alters an existing enum column**, so a database created before this feature keeps `account_status enum('ACTIVE','CLOSED')` and writing `SUSPENDED` fails. Run `db/ddl/03_account_suspension_migration.sql` (idempotent: it only adds what's missing, so it works whether or not the app has already started on the new version; until then `AccountStatusDemoSeeder` stops at its first suspended account). Adding any future `AccountStatus` value needs the same kind of `ALTER ... MODIFY COLUMN account_status enum(...)` migration plus an update of `db/ddl/01_create_tables.sql`. The hand-run DDL gives `suspended` a `DEFAULT b'0'` (Hibernate emits none) so scripts that omit it stay valid.
- **Hand-run SQL**: `db/dml/04_account_suspension.sql` mirrors suspend/update/reactivate/expire; `db/dml/01_account_operations.sql` already filters withdraw/deposit on `account_status = 'ACTIVE'`, which excludes suspended accounts.

### Paginated account search is a real Spring Data JPA `Specification` query

`GET /v1/api/accounts` (`ClientAccountController.listAccounts` → `org.bee.banking.service.AccountStatusStatementService.listAccountStatuses` → `AccountRepository.search`) retrieves accounts filtered by an optional `accountNumber`/`status`/`createdFrom`/`createdTo`/`closedFrom`/`closedTo` and paginated via a standard Spring `Pageable` (`page`/`size`/`sort` request params, auto-resolved since spring-data-commons is on the classpath — no extra config needed). `accountNumber` implements the "single account vs. all accounts" conditional lookup: it's just another AND'd `Specification` predicate (case-insensitive equality on the `AccountEntity.accountNumber` column) rather than a separate code path, so a provided-but-out-of-date-range account number still yields an empty page instead of bypassing the other filters — there's exactly one query method and one response shape (`Page<AccountStatusView>`) for both "one account" and "all accounts" callers. `AccountRepository.search()` builds a `Specification<AccountEntity>` from whichever filters are non-null and calls `accountJpaRepository.findAll(spec, pageable)` — filtering, sorting, and pagination all happen as real SQL against the database (Caffeine-cached for 10 minutes, see below), not in application code. Only `createdDate`, `closedDate`, `accountStatus`, and `accountNumber` are valid `sort` properties (`AccountRepository.validateSortProperty`, checked *before* calling `findAll` so an invalid property throws the app's own `IllegalArgumentException`/`400` rather than a raw Hibernate property-resolution exception) — anything else throws. Note `checkingAccountNumber`/`savingAccountNumber` were valid sort keys in the old in-memory version but no longer exist as separate concepts now that `AccountEntity` has a single `accountNumber` column; if you're looking at old docs/code referencing those two, they're stale.

The "pull accounts with their status" business logic — date-range validation plus mapping each `Account` to the flattened `org.bee.banking.domain.AccountStatusView` (single `accountNumber`, `accountType`, `accountStatus`, `createdDate`, `closedDate`, `firstName`, `lastName`) — lives in `org.bee.banking.service.AccountStatusStatementService`, deliberately separate from `ClientAccountService`/`AccountRepository`: `AccountRepository.search()` stays a pure data-access concern returning full `Account` entities, and `AccountStatusStatementService` owns the view/projection concern on top of it (`Page<Account>.map(...)` → `Page<AccountStatusView>`). There is deliberately no separate single-account-by-path endpoint (e.g. `GET /v1/api/accounts/{accountNumber}/status`) — it was added and then removed once the `accountNumber` query param on the search endpoint made it redundant; don't re-add it without checking with the user, since `?accountNumber=X` is the one-and-only way to fetch a single account's status/details now. If you need another account-status-derived view or report, add it to `AccountStatusStatementService`. This endpoint sits under `/v1/api/accounts`, so it's covered by the banking rate-limit gateway (see below) like every other banking endpoint.

**Default `months` lookback**: `listAccountStatuses` also takes an optional `months` (Integer). If neither `createdFrom` nor `createdTo` is given, it defaults the range to `[today.minusMonths(months), today]`, falling back to `AccountStatusStatementService.DEFAULT_LOOKBACK_MONTHS` (18) when `months` is also omitted — i.e. the endpoint's baseline behavior is "accounts created in roughly the last year and a half," not "all accounts ever." Supplying either explicit `createdFrom`/`createdTo` bound skips this default entirely and `months` is silently ignored (explicit dates always win); `months <= 0` throws `IllegalArgumentException` (`400`) regardless of whether it would've been used.

**Seed data dates are relative to `LocalDate.now()`, not fixed calendar dates** (see `AccountDataSeeder`) — this was a deliberate fix after the `months` default above initially shipped against fixed 2019-2022 seed dates, which made `GET /v1/api/accounts` return an empty page by default regardless of when the app was started. The "plain" ACTIVE seed accounts (`CH-0000088291`, `SV-0000044102`, and the `seedChecking`/`seedSavings` no-status overloads, 46 accounts total) are seeded 2-5 months back, so they always fall inside the default 18-month window and even a `months=6` query. The two `CLOSED` demo accounts (`CH-0000010004`, `SV-0000020004`) are deliberately seeded 24-30 months back — outside the default window on purpose, to demonstrate that older/closed accounts need a wider `months` (e.g. `months=36`) or an explicit `createdFrom` to surface. If you add new seed accounts, use `LocalDate.now().minusMonths(N)` rather than a fixed `LocalDate.of(...)`, or they'll silently age out of the default window over time.

**Naming note:** despite the "statement" name and the fact that these classes started life in an `org.bee.banking.statement` package, `AccountStatusStatementService` and `AccountStatusView` were later moved to `org.bee.banking.service` and `org.bee.banking.domain` respectively (to match this module's usual controller→service→repository/domain layout) — but the test class `AccountStatusStatementServiceTest` still physically lives under `src/test/java/org/bee/banking/statement/` with `package org.bee.banking.statement;`. This mismatch between the test's package/directory and the production classes' packages is intentional-but-inconsistent leftover state; it compiles fine (javac doesn't require package-to-directory matching), so don't "fix" it by moving things back without checking with the user first.

### Centralized messages and scoped exception handling

All banking exception messages *and* Slf4j log templates live in `BankingMessages` (`org.bee.banking.messages`) as `String.format`/`{}`-style constants — grep there before adding a new error/log string in the banking module. `BankingExceptionHandler` is a `@RestControllerAdvice(basePackages = "org.bee.banking")`, so it only intercepts exceptions thrown from banking controllers; `retail` and `events` controllers catch and translate their own errors inline (see `EventController.receiveEvent`'s try/catch mapping `JsonProcessingException` → 400, everything else → 500).

### Banking API gateway / rate limiter runs as a `Filter`, not through controllers

`org.bee.banking.gateway` implements a lightweight API-gateway ingress layer in front of *every* banking controller path (`/v1/api/accounts/*`, `/v1/api/locations`, `/v1/api/locations/*`, `/v1/client/*`, `/v1/payment/*`, `/notify`, `/notify-sms`, `/report`, `/bff/v1/portal/*` — see `BankingGatewayConfig.BANKING_URL_PATTERNS`, shared by all three filters below). None of the filters is a `@Component` — annotating one directly would make Spring Boot also auto-register it for `/*` — so each is registered via its own `FilterRegistrationBean` in `BankingGatewayConfig`. If you add a new banking controller or endpoint, add its path to `BANKING_URL_PATTERNS` or it won't get a `btid`/won't be rate-limited.

Three filters run in a fixed order (`BusinessTransactionIdFilter` at `Ordered.HIGHEST_PRECEDENCE`, `BankingRateLimitFilter` at `HIGHEST_PRECEDENCE + 1`, `BankingRequestLoggingFilter` at `HIGHEST_PRECEDENCE + 2` — lower value runs first):

1. **`BusinessTransactionIdFilter`** generates a `UUID` "btid" for every request, puts it in SLF4J MDC under key `"btid"`, echoes it as the `X-BTID` response header, and clears it in a `finally` block (MDC is thread-local; Tomcat reuses worker threads, so leaving a stale value would bleed into an unrelated later request on that thread). Runs *first* specifically so `BankingRateLimitFilter`'s own rejection logs also carry a `btid`. The `logging.pattern.console` entry in `application.yml` includes `[btid=%X{btid:--}]`, so **every log line in every layer** (controller, service, repository — via SLF4J/MDC propagation, not a threaded parameter) automatically shows the same id for one request; non-request logs (startup, scheduled tasks) show `[btid=-]`.
2. **`BankingRateLimitFilter`** runs before `DispatcherServlet`, so it writes the HTTP response itself (`response.setStatus(...)` + plain-text body) rather than throwing — `BankingExceptionHandler` never sees a rejected request, since `@RestControllerAdvice` only intercepts exceptions from within controller method execution. Two checks, in order: (1) the request must carry the `banking.rate-limit.customer-header-name` header (default `X-Customer-Id`) → `400` if missing/blank; (2) that customer ID is capped at `banking.rate-limit.requests-per-day` (default 1000) requests/day, tracked in `CustomerRateLimiter`'s in-memory `ConcurrentHashMap<customerId, AtomicInteger>` with a single shared day-rollover check (same pattern as `NotificationService`'s SMS daily limit) → `429` once exhausted. Every response gets `X-RateLimit-Limit`/`X-RateLimit-Remaining` headers. `banking.rate-limit.enabled: false` disables just this filter (btid stamping still happens).
3. **`BankingRequestLoggingFilter`** (extends Spring's `AbstractRequestLoggingFilter`) logs every request that gets past the rate limiter — `Request <METHOD> <uri?query>, payload=<body>` at INFO, tagged with the btid — so requests the limiter rejects (missing header / `429`) are *not* body-logged (the rate limiter logs those itself). The body only exists in the cached wrapper once a controller has read it, so the line is written **after** the chain runs (`afterRequest`; `beforeRequest` is a deliberate no-op) — it still appears if the controller rejects the request. Payload is truncated to `banking.request-logging.max-payload-length` (default 2000); `dateOfBirth` values are masked to `***` (`BankingRequestLoggingFilter.mask`) — if a new request field is more sensitive than names/addresses, mask it there too. Headers are never logged. `banking.request-logging.enabled: false` removes the filter bean entirely (`@ConditionalOnProperty` on its bean method; default on). The message text already contains the HTTP method, so the template (`BankingMessages.LOG_REQUEST_RECEIVED`) doesn't add one.

### Notification gating

`NotificationService.sendEmail`/`sendSms` are `@Async` fire-and-forget methods gated by the bound `BriteEmailConfigValues`/`BriteSmsNotificationConfigValues` (`notification.email.*` / `notification.sms.*` in `application.yml`). SMS additionally enforces `dailyLimit` via an in-memory day-rolling counter in `NotificationService`. Both are invoked from `ClientAccountService` (register, withdraw) and `BankStatementService` (statement generation) — deposit does not currently trigger a notification.

### Resilience4j annotation ordering

`PaymentService.processPayment` stacks `@Retry` above `@CircuitBreaker` deliberately (see the comment on that method): Retry is the outer aspect so each retry attempt still respects the breaker's state, and only `@Retry` declares a `fallbackMethod` — if `@CircuitBreaker` also had one, it would swallow failures before `@Retry` ever saw them.

### Liveness/readiness probes

`management.endpoint.health.probes.enabled: true` (in `application.yml`) turns on Spring Boot's Kubernetes-style health groups, exposed at `/actuator/health/liveness` and `/actuator/health/readiness`. Liveness only reflects `LivenessStateHealthIndicator` (the JVM process), so it stays `UP` even if MySQL is down. Readiness is explicitly configured (`management.endpoint.health.group.readiness.include: readinessState,db`) to also fold in the `DataSourceHealthIndicator`, so it flips to `DOWN` if the MySQL connection is lost — that's deliberate, since this app can't actually serve most endpoints without the datasource. If you add other hard dependencies (e.g. a new external service health indicator), add them to that same `readiness.include` list rather than relying on the default `/actuator/health` aggregate.

### App-wide execution-time logging via Spring AOP

`org.bee.common.logging.ExecutionTimeLoggingAspect` is a Spring AOP `@Aspect`/`@Around` advice with pointcut `within(@org.springframework.web.bind.annotation.RestController *)` — it wraps *every* `@RestController` method in the app (banking, retail, events, configs, versioning, sample; not just one module) in a `System.nanoTime()` timer and logs `"<ClassName>.<method>(..) executed in <N> ms"` at INFO, using try/finally so failed requests still get logged. Requires `spring-boot-starter-aop` (pulls in AspectJ weaver) — added specifically for this, since nothing else in the app used Spring AOP directly before (Resilience4j's `@CircuitBreaker`/`@Retry` are also AOP-based, but that starter brought its own aspect support). If you add a new controller anywhere under `org.bee`, it's automatically covered — no per-controller change needed. Don't confuse this with `AccountStatusStatementService.listAccountStatuses`'s own `log.debug` calls — those are business-level logging, this aspect is purely infrastructure/observability at the HTTP-method-call boundary.

### Account search results are cached for 10 minutes (Caffeine)

`AccountStatusStatementService.listAccountStatuses` (backing `GET /v1/api/accounts`) is `@Cacheable(cacheNames = AccountStatusStatementService.ACCOUNT_SEARCH_CACHE)` — the cache name is a public constant (`"accountSearch"`) shared with the evicting side. TTL is configured once, in `application.yml`, as `spring.cache.caffeine.spec: expireAfterWrite=10m` (Caffeine's cache manager is auto-configured by Spring Boot since `caffeine` is on the classpath and `spring.cache.type: caffeine`); there's no per-annotation TTL — `spring-boot-starter-cache`'s default `ConcurrentMapCacheManager` doesn't support TTL at all, which is why Caffeine was added as a dependency specifically for this. `@EnableCaching` lives on `SpringBootProjectsApplication`.

This is safe to cache because `AccountStatusView` never exposes balance — only `accountNumber`, `accountType`, `accountStatus`, `createdDate`, `closedDate`, `firstName`, `lastName`, none of which withdraw/deposit ever change. The mutations that *do* change a field this view shows are `ClientAccountService.registerNewClientAccount` (a new account appears), `.closeAccount`/`.closeAccounts` (`accountStatus`/`closedDate` change) and every `AccountSuspensionService` mutation (status and the suspension fields change) — all carry `@CacheEvict(cacheNames = AccountStatusStatementService.ACCOUNT_SEARCH_CACHE, allEntries = true)`. If you add another account mutation that changes a field in `AccountStatusView`, evict this same cache from it; if you cache anything that *does* expose balance (e.g. the full `Account`), you must evict on withdraw/deposit too, or callers will read stale balances for up to 10 minutes.

### Banking OpenAPI spec is hand-written and served statically (not generated)

`src/main/resources/static/openapi/banking-openapi.yaml` (OpenAPI 3.0.3) documents every banking endpoint (`/v1/api/accounts/**`, `/v1/api/locations/**`, `/v1/client/name`, `/v1/payment/process`, `/notify`, `/notify-sms`, `/report`). **It is not generated from the code** — there's no springdoc, so it won't notice when a controller, DTO, validation rule, or exception mapping changes. If you change any of those in the banking module, update the spec in the same change (request/response schemas, `required` lists, status codes, and the plain-text-vs-JSON error split below). Validate edits with `openapi-spec-validator` (`pip install openapi-spec-validator`); it only checks structure, not that the spec still matches the controllers.

Things the spec encodes that are easy to get wrong when editing it: business-rule failures from `BankingExceptionHandler` and the gateway filters are `text/plain`, while `@Valid` body failures fall through to Spring Boot's default JSON error (`SpringErrorResponse`); `X-Customer-Id` is modeled as an `apiKey` security scheme but is only a rate-limit key, not authentication; `Account` populates only the checking-or-saving field pair matching `accountType`; `Customer` responses include a derived `dateOfBirthValid` (Jackson serializing `isDateOfBirthValid()`); `WithdrawalRequest.withdrawalDate`/`withdrawalStatus` are accepted but ignored; dates in requests use `MM/dd/yyyy` for `dateOfBirth` but ISO `yyyy-MM-dd` everywhere else. In YAML flow sequences, quote strings containing `,` (e.g. `['createdDate,desc']`) or they split into separate items, and quote plain scalars containing `: `.

Swagger UI is the `org.webjars:swagger-ui` webjar plus `webjars-locator-lite` (so asset URLs need no version) and a static page, `static/swagger-ui/index.html`, which loads the spec by relative URL so it works under the `/brite` context path: `http://localhost:8081/brite/swagger-ui/index.html`, spec at `/brite/openapi/banking-openapi.yaml`. Those static paths aren't in `BankingGatewayConfig.BANKING_URL_PATTERNS`, so loading the UI needs no `X-Customer-Id`; its "Try it out" calls do, via the Authorize button.

### `db/` holds hand-runnable SQL (DDL, seed data, DML) that mirrors the entities and seeder

`db/ddl/01_create_tables.sql` is the schema Hibernate 6.6's `MySQLDialect` generates from the JPA entities (banking + `EventEntity`), so it matches what `ddl-auto: update` builds on a fresh database — including Hibernate's own FK constraint names, deliberately kept so a later `update` finds nothing to change. `db/data/01_seed_customers_accounts.sql` was *generated by parsing* `AccountDataSeeder` (same 52 accounts, dates as `DATE_SUB(CURDATE(), INTERVAL n MONTH)` to stay relative like `LocalDate.now()`); `db/data/05_...` mirrors `AccountStatusDemoSeeder`'s 40 closed/suspended accounts, and `db/ddl/03_account_suspension_migration.sql` upgrades an older database. `db/dml/` has the writes/queries as plain SQL, and `db/README.md` lists every file. **None of this is executed by the app** — nothing to keep in sync automatically — so when you add/rename/retype a column on an entity, or change `AccountDataSeeder`'s accounts, update the matching `db/` scripts in the same change. To regenerate the DDL without a database connection, boot Hibernate with `jakarta.persistence.schema-generation.scripts.action=create` + `hibernate.boot.allow_jdbc_metadata_access=false` (Hibernate 6.6 moved `SchemaExport` out of hibernate-core, so the JPA script properties are the easy route); Boot 3.4's physical naming strategy is Hibernate's `CamelCaseToUnderscoresNamingStrategy`. The DML scripts were reviewed but not executed (they use MySQL session variables and `SELECT ... INTO @var`); the DDL and `data/` scripts were verified by loading them into H2 in MySQL mode.

## Testing

Most existing tests use `@SpringBootTest` + `MockMvc` (see `ProductControllerTest`, `BriteConfigValuesControllerTest`, `SpringBootProjectsApplicationTests`). Because the full context boots, those tests need MySQL reachable as described above — and, since the banking JPA migration, so does `AccountDataSeeder`'s `@PostConstruct` seeding, which runs as part of that same context boot (you'll see "Seeding demo banking accounts" or "Accounts table already has data" in these tests' output too).

`ClientAccountServiceTest`, `AccountStatusStatementServiceTest`, `CustomerRateLimiterTest`, `BankingRateLimitFilterTest`, `BusinessTransactionIdFilterTest`, and `BankingRequestLoggingFilterTest` (`src/test/java/org/bee/banking/...`) are deliberately plain JUnit 5 + Mockito unit tests with **no** `@SpringBootTest` — none of `ClientAccountService`'s mocked collaborators, `AccountStatusStatementService`, `CustomerRateLimiter`, `BankingRateLimitFilter`, `BusinessTransactionIdFilter`, or `BankingRequestLoggingFilter` have Spring/MySQL dependencies of their own (mocked repository facades, in-memory counters, plain-POJO collaborators, mocked `HttpServletRequest`/`Response`/`FilterChain`, direct `MDC` reads), so these run standalone even without MySQL up. (`BankingRequestLoggingFilterTest` is the one that doesn't use Mockito: it drives the filter with `MockHttpServletRequest` and a stand-in chain that reads the body, then asserts on log output via a Logback `ListAppender` attached to the filter's logger.) When adding tests for banking business logic (validation rules, status transitions, balance math, rate limiting), prefer this pattern - mock `AccountRepository`/`TransactionRepository`/`WithdrawalRepository` rather than instantiating them, since they're JPA-backed now and need a real `AccountJpaRepository`/etc. - over booting the full context; reserve `@SpringBootTest`/`MockMvc` for controller-layer/wiring tests.

**`AccountRepositoryTest` is the one exception**: since `AccountRepository.search()` now builds a real `Specification` query, a Mockito-mocked `AccountJpaRepository` could only assert "was `findAll(spec, pageable)` called," not that the resulting SQL/filtering is actually correct - that needs a real database. It's a `@DataJpaTest` (`@ContextConfiguration(classes = SpringBootProjectsApplication.class)` + `@TestPropertySource` clearing `spring.jpa.properties.hibernate.dialect` and forcing `ddl-auto=create-drop`, since `application.yml` hardcodes the MySQL dialect and `@DataJpaTest`'s embedded-H2 swap only replaces the datasource, not that dialect override) using the embedded H2 dependency instead of live MySQL - each test runs in a rolled-back transaction against a fresh schema. `AccountRepository` itself is a plain `@Repository` class, not a Spring Data interface, so it's constructed directly in `@BeforeEach` around the real `@Autowired AccountJpaRepository`, rather than relying on `@DataJpaTest`'s component scan (which only auto-creates entities/Spring Data repository beans) to provide it.

`ExecutionTimeLoggingAspectTest` (`org.bee.common.logging`) and `AccountSearchCachingTest` (`org.bee.banking.service`) follow the same no-Spring-context pattern for the AOP/caching additions above: the former calls `ExecutionTimeLoggingAspect.logExecutionTime(...)` directly against a mocked `ProceedingJoinPoint` rather than verifying the AspectJ pointcut actually weaves (that's a Spring/classpath-wiring concern, not business logic); the latter uses plain reflection to assert `@Cacheable`/`@CacheEvict` are present and reference the same cache name, since actually exercising cache population/eviction/TTL requires a live `ApplicationContext` with the proxy applied — the `SpringBootProjectsApplicationTests`/`@SpringBootTest` suite exercises the real thing incidentally (its MockMvc calls flow through the aspect, which is why its test output shows `ExecutionTimeLoggingAspect` log lines).

Suspension tests follow the same split: `AccountSuspensionServiceTest`/`AccountSuspensionExpiryJobTest` are plain Mockito unit tests (time-window rules, partial update, expiry hook); `AccountSuspensionControllerTest` is standalone MockMvc (no Spring context, no MySQL) with the real `BankingExceptionHandler`; the state rules (suspended blocks withdraw/deposit, reactivate, expiry query, close-from-suspended) are in `AccountRepositoryTest` against H2 because they're real SQL; `AccountStatusDemoSeederTest` runs both seeders on H2 through a minimal `@Import` context (beans imported that way get their class name as bean name, which is why the seeder depends on the base seeder by constructor injection, not `@DependsOn("accountDataSeeder")`).
