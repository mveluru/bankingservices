# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A Spring Boot 3.5 (Java 25) REST application (`org.brite`, artifact `bankingservices`) that demonstrates several backend patterns in isolated modules: `@ConfigurationProperties` binding, async notification processing, Resilience4j circuit breaking/retry, MapStruct mapping, and Spring Data JPA — see `../README.md` for the full endpoint table and sample `curl` requests.

## Project naming

The Maven artifact, `spring.application.name` and README title are `bankingservices` (lowercase); the main class is `org.brite.BankingServicesApplication` (tests: `BankingServicesApplicationTests`). The Java packages were renamed from `org.bee.*` to `org.brite.*` (groupId `org.brite` too); the database (`db_example`) deliberately keeps its name. **The context path `/brite` must not change**: the `bankinguiportal` project reaches this service only by URL (`BANKING_BACKEND_URL` / `NEXT_PUBLIC_API_BASE_URL` = `http://localhost:8081/brite`), so renaming it breaks the portal, the OpenAPI `servers`, CORS setup and every curl sample. The GitHub repo (`mveluru/bankingservices`) and the local folder (`~/IdeaProjects/gitprojects/bankingservices`) carry the same name; both were renamed from `springbootexampleprojects`. Claude Code memory is keyed by the folder path, so it was copied to the new project key when the folder was renamed.

OpenAPI sync). Read the relevant file before changing that layer.

Skills (`.claude/skills/`): `banking-change-checklist` (which code/`db/`/OpenAPI/README/test files move together for each kind of banking change) and `account-lifecycle-smoke-test` (user-invoked only: exercises suspend/update/reactivate/close/expiry against the running app with throwaway accounts, then closes them; it never deletes rows). Hooks (`.claude/settings.json`): `banking-sync-reminder.py` (post-edit reminders + OpenAPI validation) `doc-sync.py` (blocks finishing a turn whose functional changes lack documentation updates; see below), and `db-destructive-guard.py` (asks before a command drops, truncates, deletes rows from or drops columns of a banking table - `accounts`, `customers`, `account_transactions`, `withdrawal_history`, `bank_locations`, `bank_location_services`, `bank_employees`, `bank_employee_credentials`, `customer_credentials`, `security_answers` - or runs `DROP DATABASE`, `db/ddl/02_drop_tables.sql` or `db/dml/03_reset_banking_data.sql`; non-banking tables such as `events` pass through; when the target is accounts/customers/employees/logins its prompt also says to prefer closing an account over deleting rows). `banking-sync-reminder.py` also covers the employee/login classes (privilege and ACTIVE-login rules, credential handling, JWT, gateway patterns, seeders and migrations).

**Documentation is enforced, not optional.** `doc-sync.py` runs on `UserPromptSubmit` (snapshots the working tree: a content hash of every modified/untracked/deleted file) and on `Stop` (compares with that snapshot). If the turn changed functionality - `src/main/**` code or config, `pom.xml`, `db/**` scripts, `.claude/hooks|skills|settings.json` - without updating the docs that describe it, the stop is **blocked** and Claude must update them: `README.md` for any code/config/pom change; `.claude/CLAUDE.md` or `.claude/rules/**` for any functionality change; `banking-openapi.yaml` for controllers, requests, exceptions, response DTOs, BFF and gateway config; `db/**` (a script and/or `db/README.md`) for entities and seeders. It looks at the real working tree, so edits made through Bash count too; files already dirty before the turn count only if they change again; committing is not a change; test files and local-only files (`CLAUDE.local.md`, `settings.local.json`) never trigger it. It blocks at most twice per turn (no loops). For a change that truly needs no documentation (pure refactor, typo) end the final message with a line `Docs: no update needed (reason)`. Self-test: `python3 -m unittest discover -s .claude/hooks -p 'test_*.py'`. Update `doc-sync.py`'s path rules (and its test) when you add a new kind of functional file or document.

## Commands

**Java 25 is required** (`java.version` = 25 in `pom.xml`; classes are bytecode 69). Run Maven and the app on JDK 25: `export JAVA_HOME=$(/usr/libexec/java_home -v 25)` and check `mvn -v`. On a JDK older than 25 the build fails at the compiler; building with 25 but running on an older JVM fails with `UnsupportedClassVersionError`. Spring Boot is 3.5.x (currently 3.5.16, Spring Cloud 2025.0.3) because Boot 3.4's Spring Framework/ASM can't read Java 25 class files (every `@SpringBootTest` failed with "Unsupported class file major version 69") and its managed Byte Buddy/Mockito predates Java 25. Don't downgrade Boot or `java.version` without re-running the full suite. Spring Data JPA 3.5: use `Specification.unrestricted()`, not the deprecated `Specification.where(null)`. If `mvn` is run while the app is running under DevTools, the rebuilt classes restart the app on whatever JVM launched it, so restart the app on the same JDK as the build.

```bash
mvn clean compile          # compile
mvn test                   # run all tests + generate a JaCoCo coverage report
mvn test -Dtest=ClassName                         # run a single test class
mvn test -Dtest=ClassName#methodName              # run a single test method
mvn spring-boot:run        # start the server (port 8081, context path /brite)
```

`mvn test` also runs the `jacoco-maven-plugin` (`prepare-agent` + `report`; Boot does **not** manage this plugin, so its version is pinned via the `jacoco.version` property in `pom.xml` — 0.8.14+ is needed for Java 25 class files, and an unpinned plugin silently floats to the latest release), producing `target/site/jacoco/index.html` (plus `jacoco.csv`/`jacoco.xml`) — open the HTML file directly in a browser, no server needed. It's build output under `target/`, so it's git-ignored and regenerated on every test run.

**A live MySQL instance is required to run the app or most of the test suite.** The datasource in `../src/main/resources/application.yml` (`spring.datasource.url: jdbc:mysql://localhost:3306/db_example`) is real — there is no H2/test profile override for the app itself (`src/test/resources` doesn't exist), so `@SpringBootTest` classes boot the full context against that same MySQL instance. `spring.jpa.hibernate.ddl-auto: update` auto-creates/updates tables (`accounts`, `customers`, `account_transactions`, `withdrawal_history`, `bank_locations`, `bank_location_services`, `bank_employees`, `bank_employee_credentials`, `customer_credentials`, `security_answers`) on startup. The one exception is `AccountRepositoryTest`, a `@DataJpaTest` that swaps in embedded H2 (already a dependency) instead — see Testing below.

Base URL for every endpoint: `http://localhost:8081/brite` (context path `/brite` is configured in `application.yml`). Interactive API docs for the banking module: `http://localhost:8081/brite/swagger-ui/index.html` (see "Banking OpenAPI spec" below). If 8081 is already taken (e.g. an IDE-launched instance), run a second copy with `mvn spring-boot:run -Dspring-boot.run.arguments=--server.port=8082` rather than killing the other one.

## Architecture

### Module layout

Each top-level package under `org.brite` is a self-contained vertical slice (controller → service → repository), independently scanned via `scanBasePackages`/`@ConfigurationPropertiesScan` in `BankingServicesApplication`:

- `org.brite.banking` — client/account registration, withdraw/deposit, bank statements, async notifications, Resilience4j payment demo, a `Filter`-based API gateway (`org.brite.banking.gateway`: btid tracing, per-customer rate limiting, request-body logging) fronting the whole module, staff/employee endpoints and employee/customer logins (`StaffController`, `LoginController`; see "Bank employees" below and `.claude/rules/banking/employees-and-logins.md`), a hand-written OpenAPI spec + Swagger UI (`src/main/resources/static/openapi`, `static/swagger-ui`), account suspension (`AccountSuspensionService`, suspend/update/reactivate endpoints, a scheduled expiry job) and paginated/single account-status lookup (`AccountStatusStatementService` in `org.brite.banking.service`, view DTO in `org.brite.banking.domain`), and a real JPA data model (`org.brite.banking.entity` + `org.brite.banking.repository.jpa`) persisted to MySQL — see "JPA-backed persistence" below
  - **BFF for the banking UI portal**: `org.brite.banking.bff` (`/bff/v1/portal/*`: `home`, `accounts/{n}/overview`, `accounts/open`, and mutations `accounts/withdraw`, `accounts/deposit`, `accounts/{n}/close`, each returning the refreshed `AccountOverviewResponse`; plus `POST accounts/{n}/statement?beginDate=&endDate=` returning the `BankStatement`, a POST because it emails/SMSes) composes the banking services in process into screen-shaped DTOs; tunables in `banking.portal.*`, CORS via `PortalCorsConfig` (GET/POST/PUT/PATCH/OPTIONS, headers `Content-Type`, `X-Customer-Id`, `Authorization`). **Customer login, login status and password** each have their own BFF controller + service (paths unchanged): `CustomerLoginController` → `CustomerLoginPortalService` (open `POST /bff/v1/portal/login`; staff `POST /bff/v1/staff/customers/{id}/login`), `CustomerLoginStatusController` → `CustomerLoginStatusPortalService` (staff `PUT /bff/v1/staff/customers/{id}/login-status`), `CustomerPasswordController` → `CustomerPasswordPortalService` (customer `PUT /bff/v1/portal/password`, `PUT .../security-questions`, open `GET .../security-questions/catalog`, `POST .../password-reset[/questions]`; staff `PUT /bff/v1/staff/customers/{id}/password`). Details of the customer calls: open `POST login?state=` (`LoginService.customerLogin` then `PortalOrchestrationService.home(state, customerId)` → `PortalLoginResponse{accessToken, tokenType, expiresIn, customer, home}`, `Cache-Control: no-store`, `toString` omits the token; a failed login never builds home), `GET security-questions/catalog`, `POST password-reset/questions`, `POST password-reset`, and token-protected `PUT password` and `PUT security-questions` (customer id from `CustomerAuthenticationFilter.CUSTOMER_ATTRIBUTE` via `CustomerAccessService.requireAuthenticated`, never the body); they only delegate to `CustomerCredentialService`/`PasswordResetService`. Those open BFF paths are in `CustomerAuthenticationFilter.OPEN` (a new open portal path must be added there). **Customers see the branch/ATM, never the employee**: `PortalActivityItem` carries `bankLocationName/Type/City/State` (no employee field exists) and **`BankStatementService.generateStatement` itself clears `employeeNumber/Name/Role`** on every line (`AccountTransaction.withoutStaffIdentity()`, JSON shape unchanged, values null, location kept), so the banking `GET /v1/api/accounts/{n}/statement`, the portal statement and the emailed/SMSed statement all hide staff identity; the stored transaction keeps it, and a future staff-facing statement needs its own method that keeps the employee fields (`BankStatementServiceTest`). The *customer* portal has no suspend/reactivate (staff-only). Opening an account through the portal does not create a login. **Staff portal BFF** (`/bff/v1/staff/*`, the employee counterpart: `StaffPortalController` → `StaffPortalService`, `StaffPortalAuthController` → `StaffPortalAuthService`): open `POST login` (`LoginService.staffLogin` → `StaffPortalLoginResponse{accessToken, tokenType, expiresIn, employee: PortalEmployee, branch: PortalLocation or null}`, `no-store`, token out of `toString`; `PortalOrchestrationService.location(id)` builds the branch card), open `GET security-questions/catalog`, `POST password-reset/questions`, `POST password-reset`, and employee-token calls: `PUT password`, `PUT security-questions`, `GET accounts/{n}/overview` (`EmployeeService.requirePrivilege(VIEW_ACCOUNT)` then `PortalOrchestrationService.overview`), `POST accounts/withdraw|deposit?locationId=`, `POST accounts/{n}/suspend|reactivate|close`, `PATCH accounts/{n}/suspension` (all call the banking `StaffAccountService` first — which enforces the privilege — and only then rebuild the refreshed `AccountOverviewResponse`; a rejection builds nothing), `GET employees` / `employees/{n}` (`PortalEmployee` cards: no email/phone/internal ids), and the employee administration (`employees/{n}/login-status|password`) via `StaffLoginService`; the *customer* administration calls (`customers/{id}/login|login-status|password`) are served by the three customer controllers above, not `StaffPortalController`. The acting employee is `StaffAuthenticationFilter.EMPLOYEE_ATTRIBUTE` (the filter now also covers `/bff/v1/staff/*`, with the login/catalog/reset calls in its `OPEN` set) — never the body or a header; the BFF adds no rules. Customer-token paths (`/bff/v1/portal/*`) and employee-token paths (`/bff/v1/staff/*`) reject each other's tokens with 403. `/bff/v1/staff/*` is in `BANKING_URL_PATTERNS`. See `.claude/rules/banking/bff-layer.md`.
- Retail (product catalog) used to live here; it moved to the separate `retailservice` project (`~/IdeaProjects/gitprojects/retailservice`, port 8082, context path `/retail`). Don't re-add it.
- Event ingestion (`org.brite.events`, `POST /api/events`) moved to the separate `eventservice` project (`~/IdeaProjects/gitprojects/eventservice`, port 8085, context path `/event`). It uses the existing `events` table in this same `db_example` database (`ddl-auto: none`); that table is no longer created or touched by this app, and its DDL/sample rows live in eventservice's `db/`. Don't re-add the events code here.
- The main class sits in the root `org.brite` package (there is no `org.brite.configs` package any more). The `notification.email.*`/`notification.sms.*` `@ConfigurationProperties` classes (`BriteEmailConfigValues`, `BriteSmsNotificationConfigValues`) live in `org.brite.banking.domain` and are used by banking's `NotificationService`. The `/v1/configs` echo controller, its service and `BriteApplicationConfigValues` moved to the separate `configservice` project (`~/IdeaProjects/gitprojects/configservice`, port 8083, context path `/config`); don't re-add them.
- The API-versioning demos (`org.brite.restapi.versioning`, `/apiversion`) moved to the separate `restapiversionservice` project (`~/IdeaProjects/gitprojects/restapiversionservice`, port 8084, context path `/restapi`); don't re-add them.
- `org.brite.sample` — a small standalone lookup demo, unrelated to the other modules
- `org.brite.common` — cross-cutting concerns that apply app-wide rather than to one module (currently just `org.brite.common.logging.ExecutionTimeLoggingAspect`); explicitly added to `scanBasePackages` in `BankingServicesApplication` since it's outside the modules listed above

### Persistence: banking is JPA/MySQL

The whole **banking** module persists via JPA — real accounts, customers, transactions, and withdrawal history rows in MySQL that survive app restarts.

### JPA-backed persistence for banking (entities, repositories, and the domain-object mapping seam)

Banking used to be a `ConcurrentHashMap`-backed mock store; it's now backed by real JPA entities. The **domain objects** (`Account`, `Customer`, `Address`, `AccountTransaction`, `WithdrawalForm` in `org.brite.banking.domain`) that the service/controller layers use are unchanged, so `ClientAccountService`, `BankStatementService`, `AccountStatusStatementService`, and every controller/DTO needed **zero changes** for this migration — all the mapping happens inside the repository classes:

- **Entities** (`org.brite.banking.entity`): `AccountEntity` (one row per real account — see below), `CustomerEntity`, `AddressEmbeddable` (`@Embeddable`, inlined into `CustomerEntity`/`WithdrawalHistoryEntity`, no separate table), `AccountTransactionEntity`, `WithdrawalHistoryEntity`.
- **Raw Spring Data repositories** (`org.brite.banking.repository.jpa`): `AccountJpaRepository` (extends `JpaRepository` + `JpaSpecificationExecutor` for dynamic filtering), `CustomerJpaRepository`, `AccountTransactionJpaRepository`, `WithdrawalHistoryJpaRepository`. Application code never touches these directly.
- **Facade repositories** (`org.brite.banking.repository`, same package/class names as before the migration): `AccountRepository`, `TransactionRepository`, `WithdrawalRepository` now wrap the JPA repositories above, mapping entity ↔ domain object internally (`AccountRepository.toDomain`/`toEntity` etc.) so their **public method signatures are unchanged** (`findByAccountNumber`, `search`, `save`, `withdraw`, `deposit`, `closeAccount` on `AccountRepository`; `recordTransaction`/`findByAccountNumber` on `TransactionRepository`; `createWithdrawal` on `WithdrawalRepository`). This is why `ClientAccountServiceTest`/`AccountStatusStatementServiceTest`, which mock these facade classes, didn't need to change at all — they never cared about the in-memory-vs-JPA implementation detail.

**Bank locations** (`BankLocationEntity` + `BankAddressEmbeddable` → `bank_locations`, with the `Set<BankOperationServices>` as an `@ElementCollection` in `bank_location_services`; domain shapes `BankLocations`/`BankAddress`/`LocationType`/`BankOperationServices` in `org.brite.banking.domain`) model branch offices and ATMs. `LocationType` is `OFFICE`/`ATM`/`BOTH`; `opensAt`/`closesAt`/`phoneNumber` are the *office's* and are null for `ATM`. Hours are 08:00-16:00 wall-clock in `timeZone` `America/Chicago` (not the literal "CST", so daylight saving is handled). `BankLocationDataSeeder` seeds 20 locations when the table is empty (same run-once rule as `AccountDataSeeder`; `BankLocationDataSeederTest` runs it against H2). `GET /v1/api/locations` (`BankLocationController` → `LocationBasedOperationService` → `LocationBasedOperationRepository`, the facade over `BankLocationJpaRepository` that maps entity → `BankLocations`) is a `Specification` search like the account one: optional `type`/`city`/`state`/`zip`/`service` filters plus `Pageable` (default `size=20`, `sort=name`; valid sort keys `name`, `locationType`, `city`, `state` — city/state are remapped to the embedded `address.*` paths, checked before the query so a bad one is a `400`). **`type` matches by capability, not stored value**: `OFFICE` → `OFFICE`+`BOTH`, `ATM` → `ATM`+`BOTH`, `BOTH` → `BOTH` only. It isn't cached. `GET /v1/api/locations/{id}` (`LocationBasedOperationService.getLocation`) returns one location or throws `LocationNotFoundException`, which `BankingExceptionHandler` maps to a plain-text `404` — unlike accounts, this one-record path-variable endpoint does exist, since locations have a stable numeric id (both the list and `/*` patterns are in `BANKING_URL_PATTERNS`). `BankATMLocations` is still an empty placeholder class.

**Bank employees** (`EmployeeEntity` → `bank_employees`; domain `Employee`/`EmployeeRole`/`EmployeePrivilege`/`EmployeeStatus` in `org.brite.banking.domain`; `EmployeeJpaRepository` + read-only facade `EmployeeRepository`) are the staff profiles: `TELLER` (view/deposit/withdraw), `MANAGER` (plus suspend/update-suspension/reactivate/close and branch reports) and `AREA_MANAGER` (everything, incl. `MANAGE_EMPLOYEES`). **Privileges come from the role (`EmployeeRole.getPrivileges()`), not a column**, and `Employee.hasPrivilege` is false unless the status is `ACTIVE`. `bankLocationId`/`supervisorId` are plain ids, not FKs; area managers have a `region` and no branch. `EmployeeDataSeeder` seeds 21 (3/6/12) when the table is empty, after `BankLocationDataSeeder`; mirror `db/data/07_seed_bank_employees.sql`. **Enforcement lives only on the staff endpoints** (`StaffController`, `/v1/api/staff/*`, in `BANKING_URL_PATTERNS`): the acting employee is the subject of the verified employee JWT (`StaffAuthenticationFilter` puts it in the `banking.authenticatedEmployee` request attribute; see "Staff endpoints require the employee token" below), `EmployeeService.requirePrivilege` checks ACTIVE + role privilege *before* `StaffAccountService` delegates to `ClientAccountService`/`AccountSuspensionService` (no/invalid token → 401 from the filter, unknown → 404 `EmployeeNotFoundException`, inactive/lacking privilege → 403 `EmployeeNotAuthorizedException`). The existing customer and portal endpoints are deliberately unchanged (no employee check). Staff deposit/withdraw also record **who and where** on the transaction (`TransactionHandler` → `AccountTransaction`/`AccountTransactionEntity` `employeeNumber/Name/Role` + `bankLocationId/Name/Type/City/State`, snapshots, not FKs): location = `?locationId=` else the employee's branch (null for an area manager without one); customer-initiated transactions leave them null; staff identity is **not exposed to customers** (statements clear it, the portal activity shape has no employee field; only the branch/ATM is shown); migration `db/ddl/05_transaction_handler_migration.sql`. `GET .../staff/employees[/{n}]` lists (MANAGE_EMPLOYEES) or reads a profile (own, or MANAGE_EMPLOYEES).

**Employee logins** (`EmployeeCredentialEntity` → `bank_employee_credentials`, its own table; domain `EmployeeCredential`; facade `EmployeeCredentialRepository`; `EmployeeCredentialService`): username (lowercase, `^[a-z0-9._-]{3,50}$`) + an **exactly-8-digit password stored only as a BCrypt hash** (`spring-security-crypto` only, not the Spring Security web stack; `PasswordEncoderConfig`). `createLogin(employeeNumber, username, password)` and `verify(username, password)` (returns the `Employee`; `InvalidCredentialsException` → 401 with one message for unknown user and wrong password, `EmployeeLockedException` → 423, `EmployeeNotAuthorizedException` → 403 if the password is right but the employee isn't ACTIVE). Wrong passwords are counted and lock the login after `banking.employee-login.max-failed-attempts` (5) for `lockout-minutes` (15) — an 8-digit password has only 10^8 combinations, so the lock is the real protection; `verify` uses `noRollbackFor` so the count survives the thrown exception (`EmployeeCredentialPersistenceTest` runs outside a test transaction to prove it). **Login endpoints** (`LoginController`): `POST /v1/api/staff/login` (returns the `Employee`) and `POST /v1/api/customers/login` (returns `AuthenticatedCustomer`), body `LoginRequest{username, password}`. On success they return a signed **JWT** (`StaffLoginResponse`/`CustomerLoginResponse`: `accessToken`, `tokenType`, `expiresIn`, plus the employee / `AuthenticatedCustomer`; `Cache-Control: no-store`) via `LoginService` (verify, then `JwtService.issue*`; no token on any failure). **Both tokens are enforced** (next two paragraphs): the employee token on the staff endpoints, the customer token on the customer account/portal endpoints; `X-Customer-Id` stays only a rate-limit key. JWT: HS256 via jjwt (`jjwt.version` in `pom.xml`, not Boot-managed), claims `iss`/`sub`/`type`/`role`/`jti`/`iat`/`exp`, `banking.jwt.*` (`JwtProperties`: `secret` from env `BANKING_JWT_SECRET`, >= 32 chars, never committed; blank = random key per start with a warning, so tokens die on restart; `expiration-minutes` 30; no refresh tokens). `JwtService.parse` (HMAC only, `alg: none` refused, issuer/type/expiry checked, `InvalidTokenException` → 401) is what a future bearer filter would call. Never log a token (`IssuedToken`/login responses exclude it from `toString`). `/v1/api/customers/*` is in `BANKING_URL_PATTERNS`. `BankingRequestLoggingFilter.mask` masks `password` (string, escaped-string or bare-number forms); keep it that way for any new credential field, and never put credentials in a query string. `server.error.include-stacktrace: never` is set explicitly in `application.yml` because DevTools otherwise puts stack traces in error bodies. `EmployeeCredentialSeeder` gives the 21 demo employees DEMO logins (username = email local part, password `2026` + 4-digit employee sequence, e.g. `lucas.meyer` / `20260010`); mirror `db/data/08_seed_employee_credentials.sql` (hashes only). Never log or return a password or hash.

**Staff endpoints require the employee token.** `StaffAuthenticationFilter` (registered in `BankingGatewayConfig` for `/v1/api/staff/*`, order `HIGHEST_PRECEDENCE + 2`, after the rate limiter and before request logging, which moved to `+3`) requires `Authorization: Bearer <token>` on everything except exactly `POST /v1/api/staff/login`: missing/non-Bearer/invalid/expired/forged → `401` + `WWW-Authenticate: Bearer`, a customer token → `403` (`EMPLOYEE_TOKEN_REQUIRED`); it writes plain text itself (filters are outside `@RestControllerAdvice`). On success it sets the request attribute `StaffAuthenticationFilter.EMPLOYEE_ATTRIBUTE` to the token's `sub`, and `StaffController` reads only that (`@RequestAttribute(required = false)`); the old `X-Employee-Number` header is gone and identifies nobody (`EmployeeService.requireActive` throws `InvalidTokenException` 401 when the attribute is missing, so a bypassed filter fails closed). **The token is deliberately not trusted for permissions or status**: `EmployeeService.requirePrivilege` still reloads the employee, ACTIVE login and role on every call, so a suspended login or a demotion applies immediately even though the token lives 30 minutes. Because the signing key is random when `BANKING_JWT_SECRET` is unset, every restart (including a DevTools restart) invalidates all tokens: set the variable for any real use. Tests: `StaffAuthenticationFilterTest` (servlet objects, plus a MockMvc run with the real filter and `StaffController`) and `StaffControllerTest` (uses the request attribute directly).

**Customer endpoints require the customer token and only reach the caller's own accounts.** `CustomerAuthenticationFilter` (`BankingGatewayConfig`, patterns `/v1/api/accounts/*` and `/bff/v1/portal/*`, order `+2`) requires `Authorization: Bearer <customer token>` on everything there except exactly `POST /v1/api/accounts/newaccount` and `POST /bff/v1/portal/accounts/open` (`OPEN` set, method + path; they create the customer, who has no login yet): missing/invalid/expired/forged/non-numeric-subject → `401` + `WWW-Authenticate`, an employee token → `403` (`CUSTOMER_TOKEN_REQUIRED`), login no longer ACTIVE → `403` (`CustomerCredentialService.requireActiveLogin` runs on **every** request, so a suspension applies at once; a customer whose login was removed → 401). It sets the `banking.authenticatedCustomer` request attribute (a `Long`), which `ClientAccountController` and `PortalController` read (`@RequestAttribute`, `required = false`). **Ownership** is `CustomerAccessService` (called by every handler before the service): `requireOwnAccount` (someone else's account → `AccountAccessDeniedException` 403; an account that doesn't exist is left to the operation to answer 404, which does leak existence to an authenticated customer), `requireOwnAccounts` for bulk close (whole request refused), and `requireAuthenticated` (a missing attribute fails closed with 401, never "all customers"). The account list and portal home are scoped in SQL: `AccountRepository.search`/`AccountStatusStatementService.listAccountStatuses` take a `customerId` (part of the `@Cacheable` key, so a cached page is never shared between customers; `PortalOrchestrationService.home(state, customerId)`). Customers get a login from a manager: `POST /v1/api/staff/customers/{id}/login` (`MANAGE_CUSTOMER_LOGINS`, `StaffLoginService.createCustomerLogin` → `CustomerCredentialService.createLogin`, 201); registration does not create one, so a newly registered customer can't use their account until a manager does. `PortalCorsConfig` allows the `Authorization` header. Still open: `/v1/api/locations/**`, `/v1/client`, `/v1/payment`, `/notify*`, `/report`. A customer's own close is still reachable; suspend, update-suspension and reactivate are staff-only (no customer route). The old `requireActiveLoginIfPresent` check in `ClientAccountService` stays as defence in depth. Tests: `CustomerAuthenticationFilterTest`, `CustomerAccessServiceTest`, `CustomerAccessControllerTest` (standalone MockMvc with the request attribute as the filter would set it).

**Changing your own password** (`PUT /v1/api/customers/password`, `PUT /v1/api/staff/password`, `PasswordController` → `CustomerCredentialService.changePassword` / `EmployeeCredentialService.changePassword`, body `ChangePasswordRequest{currentPassword, newPassword}`, 204): token-protected (not in the filters' `OPEN` sets); the new password is validated (8 digits) and must differ from the current one first; the current password is verified with `LoginSupport.checkPassword`, so wrong guesses count toward the login lock (401, then 423) and persist (`noRollbackFor`); the login must be ACTIVE (INACTIVE/SUSPENDED → 403); success clears the failure counters and sets `passwordChangedAt`, which makes the filters refuse every earlier token **including the caller's own** (they log in again). The identity comes from the token attribute (fail closed 401), never the body.

**Password reset with security questions.** `SecurityQuestion` (fixed catalog: `FIRST_CAR`, `FIRST_SCHOOL`, `FIRST_TEACHER`, `FIRST_PET`, `BIRTH_CITY`, `CHILDHOOD_FRIEND`; the OpenAPI enum must match) and `PasswordResetService` (`PasswordController` for the HTTP side). Three answers per employee/customer live in their own table `security_answers` (`SecurityAnswerEntity`, owner type + plain `ownerId`, **slot 1..3 with a unique index, replaced in place — never deleted**, BCrypt hash of the normalised answer: trim, lowercase, collapse whitespace; `SecurityAnswerRepository` facade). Endpoints: `PUT /v1/api/customers/security-questions` and `PUT /v1/api/staff/security-questions` (caller's token + **current password**, so a stolen token can't change the questions; checked with `LoginSupport.checkPassword`, so wrong guesses count toward the login lock), and the **open** (no-token) `POST .../password-reset/questions` and `POST .../password-reset` for customers (`/v1/api/customers/...`) and staff (`/v1/api/staff/...`). Rules: reset needs **all three** answers; an unknown username, a user with no questions and wrong answers all give the same 401 (`RESET_FAILED`) with the same BCrypt work, and `questionsFor` returns deterministic decoy questions for unknown users; wrong answers are counted per login (`resetFailedAttempts`/`resetLockedUntil` on both credential tables) and `banking.password-reset.*` (`PasswordResetProperties`, 3 attempts / 30 min) locks the reset (423) — a separate counter from the login lock; the new password is validated (8 digits) before anything else; the status is checked only after the answers are right, and a reset needs an effectively ACTIVE login so it **never undoes INACTIVE/SUSPENDED/LOCKED** (403). `verify`-style methods are `noRollbackFor` so the counters persist. **A password change invalidates older tokens**: `StaffAuthenticationFilter` (`EmployeeCredentialService.requireTokenCurrent`) and `CustomerAuthenticationFilter` (`CustomerCredentialService.requireActiveLogin(id, issuedAt)`) refuse a token whose `iat` is before `passwordChangedAt` (second precision, `LoginSupport.tokenPredatesPasswordChange`). Administrator reset without questions: `PUT /v1/api/staff/customers/{id}/password` (`MANAGE_CUSTOMER_LOGINS`) and `PUT /v1/api/staff/employees/{n}/password` (`MANAGE_EMPLOYEES`) via `StaffLoginService` → `adminSetPassword` (clears counters, leaves the status, invalidates tokens). The filters' open lists (`OPEN` sets) gained the two password-reset calls (and `CustomerAuthenticationFilter` now also covers `/v1/api/customers/*`, with the login and reset calls exempt). `BankingRequestLoggingFilter.mask` masks `password`, `newPassword`, `currentPassword` and `answer`. Limits to remember: security answers are low-entropy (an offline brute force of a leaked table is feasible), and there is no email/SMS channel. Migration `db/ddl/07_password_reset_migration.sql`. Tests: `PasswordResetPersistenceTest` (H2, outside a transaction), `PasswordControllerTest`, the filter tests (open paths, token predating the password) and the credential service tests.

**Customer logins** mirror the employee ones: `CustomerCredentialEntity` → `customer_credentials` (own table, `customerId` is a plain id), domain `CustomerCredential`, facades `CustomerCredentialRepository`/`CustomerRepository` (the latter exposes only id + name as `AuthenticatedCustomer`), `CustomerCredentialService.createLogin(customerId, username, password)` / `verify(username, password)` (returns `AuthenticatedCustomer`: id and name, never dob/phone/address). The shared rules (lowercase username, exactly-8-digit password, BCrypt, one error for unknown user vs wrong password, lockout, timing-equalising dummy hash) live in `LoginSupport`, used by both services; limits are `banking.customer-login.*` / `banking.employee-login.*` (5 failures, 15 min). Exceptions are reused: `InvalidCredentialsException` 401, `EmployeeLockedException` 423 (despite the name, also used for customers), new `CustomerNotFoundException` 404. Verified by `POST /v1/api/customers/login` (returns a JWT that `CustomerAuthenticationFilter` requires on the customer account/portal endpoints; `X-Customer-Id` remains only a rate-limit key). `CustomerCredentialSeeder` seeds DEMO logins for only the **first 10 customers** by id (`customer0001` / `20260001`, i.e. `customer` + 4-digit id, `2026` + same digits); other customers, including the portal's test customers, get none. Mirror `db/data/09_seed_customer_credentials.sql`.

**Login status and the "only ACTIVE may transact" rule** (`LoginStatus` `ACTIVE`/`INACTIVE`/`LOCKED`/`SUSPENDED` on both credential tables, with `statusReason`/`statusChangedAt`; migration `db/ddl/06_login_status_migration.sql`, column default `ACTIVE` so existing logins stay active). `LOCKED` is set automatically by `LoginSupport` after too many wrong passwords (expires at `lockedUntil`; an expired lock counts as ACTIVE via `LoginState.effectiveStatus`) or by an administrator (no expiry); `INACTIVE`/`SUSPENDED` are administrator-only, and a wrong password never changes them. **Employees:** `EmployeeService.requireActive` (so every staff endpoint) requires the employee's employment status ACTIVE **and** an ACTIVE login — no login at all is also rejected (`LoginNotActiveException`, 403). **Customers:** customer-initiated deposit/withdraw (`ClientAccountService`, `handler == null`, so BFF too) call `CustomerCredentialService.requireActiveLoginIfPresent(ownerId)` (owner found via `AccountRepository.findCustomerIdByAccountNumber`): a customer who has a login that isn't ACTIVE gets 403, but **a customer with no login is not restricted** because the customer endpoints don't require a login yet; staff-handled transactions are gated on the employee's login instead. Administration: `PUT /v1/api/staff/employees/{n}/login-status` (MANAGE_EMPLOYEES) and `PUT /v1/api/staff/customers/{id}/login-status` (new `MANAGE_CUSTOMER_LOGINS`, manager and up) via `StaffLoginService` → `changeStatus` (ACTIVE also clears the failure count and lock). `verify` on an INACTIVE/SUSPENDED login with the right password throws `LoginNotActiveException`; a LOCKED one throws `EmployeeLockedException` before the password is checked.

**Customer phone number** (`Customer.phoneNumber` ↔ `CustomerEntity.phoneNumber` → `customers.phone_number varchar(20)`): required on registration (`AccountRegistrationRequest`: `@NotBlank` + `@Pattern ^\d{3}-\d{3}-\d{4}$`, messages `VALIDATION_PHONE_*`), carried through `AccountMapper` (MapStruct, by name) and both `AccountRepository` mapper directions, returned in the `Account` response, nullable in the DB because pre-existing customers have none. It is PII like `dateOfBirth`: `BankingRequestLoggingFilter.mask` masks it in logged bodies, and the BFF never returns the full number (`AccountOverviewResponse.maskedPhoneNumber` = `***-***-0101`, `PortalOrchestrationService.maskPhone`). Seeds: base seeder gives customer N `512-555-000N`; `AccountStatusDemoSeeder` passes `512-555-0053..0092` explicitly (mirrors `db/data/05`). Existing DBs: `db/ddl/04_customer_phone_migration.sql` (idempotent) + `db/data/06_backfill_customer_phones.sql` (NULL phones of the 92 demo customers only, keyed by account number/id because customer ids drift from account ids once rows have been deleted). There is deliberately no update-phone endpoint yet. `AccountStatusView` (search rows) does not include phone.

**`AccountEntity` is one row per real account (checking OR savings), not one row per customer pairing.** The `Account` *domain* object conflates a checking and a savings account into one object with a pair of nullable fields (`checkingAccountNumber`/`checkingBalance` and `savingAccountNumber`/`savingBalance`) — that shape only ever made sense for the old map keyed by account number; a relational table models "one account number = one row" directly. `AccountRepository.toDomain(AccountEntity)` picks the checking-or-saving field pair to populate based on `entity.getAccountType()`. If you add a new field to `Account` that should persist, add it to `AccountEntity` (or `CustomerEntity`/`AddressEmbeddable` if it's a person/address field) and to both mapper directions in `AccountRepository`.

**Account numbers are generated from `accountJpaRepository.count() + 10001`**, zero-padded to 10 digits (`AccountRepository.save()`) — same scheme and starting point as the old in-memory counter, so existing seeded/documented account numbers stay valid across the migration. `AccountDataSeeder` (`@PostConstruct` on a `@Component`, not the `AccountRepository` constructor anymore) seeds the same 52 demo accounts **only if the accounts table is empty** — real MySQL persists across restarts, so unconditional reseeding (the old constructor's behavior) would create duplicates every time the app starts. If you see "Accounts table already has data; skipping demo seed" in the logs, that's expected on any restart after the first.

**Optimistic locking (`@Version` on `AccountEntity`)** replaces the old `ConcurrentHashMap.computeIfPresent`'s atomicity guarantee for `withdraw`/`deposit`/`closeAccount`: two concurrent writes to the same account row now fail one of them with an `ObjectOptimisticLockingFailureException` instead of silently losing an update. There's no retry-on-conflict logic; a concurrent-write test would need to assert the exception, not a specific final balance.

### Account number prefix drives account type resolution

Account numbers are the source of truth for account type, not a stored field on the `Account` *domain* object: `ClientAccountService.withdrawAndSaveToAccount`/`depositAndSaveToAccount` read the first two characters of the account number (`"CH"` → `CHECKING`, `"SV"` → `SAVINGS`) and reject anything else with `UNRECOGNIZED_ACCOUNT_PREFIX`. (`AccountEntity` *does* have its own `accountType` column, set at creation time - the prefix-parsing is purely a service-layer convenience for withdraw/deposit requests, not a re-derivation of unknown data.) Any code that generates or accepts account numbers (e.g. `AccountRepository.save()`) must keep producing `CH-`/`SV-`-prefixed IDs, or withdraw/deposit will fail for those accounts even though registration succeeds. The numeric part after the prefix is always zero-padded to at least 10 digits (e.g. `CH-0000088291`, `SV-0000020004`) — both `AccountDataSeeder`'s seed data and `AccountRepository.save()`'s dynamic generator (`String.format("%010d", ...)`) follow this; keep it that way if you add more seed accounts or change the generator.

### Account status (ACTIVE/SUSPENDED/CLOSED) gates withdraw/deposit

`Account` carries `accountStatus` (`AccountStatus.ACTIVE`/`SUSPENDED`/`CLOSED`), `createdDate`, `closedDate`, and the suspension fields (see "Account suspension" below). `AccountRepository.save()` defaults new accounts to `ACTIVE` with `createdDate = today` if not already set. `withdraw()`/`deposit()` throw `AccountClosedException` (mapped to `400` by `BankingExceptionHandler`) if the account is `CLOSED`, and `AccountSuspendedException` (`400`) if it is `SUSPENDED` — both checks run *before* the balance/minimum-balance checks. `POST /v1/api/accounts/{accountNumber}/close` (`ClientAccountController.closeAccount` → `ClientAccountService.closeAccount` → `AccountRepository.closeAccount`) transitions `ACTIVE` or `SUSPENDED` → `CLOSED`, stamps `closedDate` and clears any suspension; it throws `AccountClosedException` (`400`) if already closed, `AccountNotFoundException` (`404`) if the account doesn't exist. There's no reopen path for a `CLOSED` account (suspension is the reversible state). `AccountDataSeeder` seeds 52 accounts total (26 checking, 26 savings) on first startup against an empty database, including two pre-closed accounts (`CH-0000010004`, `SV-0000020004`) for demoing the closed state; everything else seeds `ACTIVE`. `AccountStatusDemoSeeder` adds 40 more (92 total): 20 `CLOSED` and 20 `SUSPENDED` — see below.

`POST /v1/api/accounts/close` is the bulk counterpart (`ClientAccountController.closeAccounts` → `ClientAccountService.closeAccounts`, body: `BulkCloseAccountsRequest{accountNumbers: List<String>}`, `@NotEmpty`-validated → `400` if empty). It's deliberately best-effort, not all-or-nothing: it loops calling `accountRepository.closeAccount(...)` **directly**, not `this.closeAccount(...)` — a self-invocation within the same Spring bean would bypass that method's own `@CacheEvict` proxy, so calling the repository straight avoids the classic Spring-AOP self-invocation pitfall. Catches `AccountNotFoundException`/`AccountClosedException` per account and routes them into `BulkCloseAccountsResult.failures` (`{accountNumber, reason}`) instead of aborting the batch; successes go into `closedAccounts`. Returns `200` always (per-item outcomes are in the body, not the HTTP status) and evicts the account-search cache once for the whole batch rather than once per account.

### Account suspension (SUSPENDED state, `AccountSuspensionService`)

`SUSPENDED` is a reversible block: **a suspended account rejects every withdraw and deposit until it is ACTIVE again.** State lives on `AccountEntity`/`Account`: `accountStatus = SUSPENDED`, `suspended` (boolean flag, true exactly while suspended), `suspendedStart`/`suspendedEnd` (`LocalDateTime`; end null = indefinite) and `suspensionNotes` (≤500 chars). The facade always writes status + flag together and treats *either* as "suspended" (`AccountRepository.isSuspended`).

- **Endpoints are staff-only** (`StaffController` → `StaffAccountService` → `AccountSuspensionService` → `AccountRepository`; need `SUSPEND_ACCOUNT` / `UPDATE_SUSPENSION` / `REACTIVATE_ACCOUNT`, managers and up, and the employee token): `POST /v1/api/staff/accounts/{n}/suspend` (body `SuspendAccountRequest{notes (required), startDateTime?, endDateTime?}`), `PATCH /v1/api/staff/accounts/{n}/suspension` (`UpdateSuspensionRequest{notes?, endDateTime?}`, at least one), `POST /v1/api/staff/accounts/{n}/reactivate`. All return the `Account`. **Customers have no route for them** on either API (they used to have `/v1/api/accounts/{n}/suspend|suspension|reactivate` and the portal equivalents; removed so a customer can't lift a suspension a manager applied: the routes are gone, not 403, and `CustomerAccessControllerTest` asserts the 404s). Update-suspension is included because shortening the end date would be a way to reactivate. A customer can still close their own account. There is deliberately no `GET .../suspension`; read suspension data from `GET /v1/api/accounts?accountNumber=` / `?status=SUSPENDED` (`AccountStatusView` carries the four fields).
- **Rules split**: time-window rules are in the service (start defaults to now and can't be future; end must be after start *and* in the future; update needs ≥1 field and a future end) and throw `IllegalArgumentException` (`400`); state rules are in the facade (closed → `AccountClosedException`, already suspended → `AccountSuspendedException`, update/reactivate when not suspended → `IllegalArgumentException`, new end must be after the *stored* start). `AccountSuspendedException` → `400` plain text.
- **Lifecycle**: suspend `ACTIVE`→`SUSPENDED`; reactivate `SUSPENDED`→`ACTIVE` and **clears** flag/start/end/notes (no history is kept); close from `SUSPENDED` is allowed and clears them too.
- **Auto-expiry**: `AccountSuspensionExpiryJob` (`@Scheduled`, `@EnableScheduling` is on `BankingServicesApplication`; `banking.suspension.expiry-job.enabled`/`interval-ms`, default 60 s) calls `AccountSuspensionService.reactivateExpiredSuspensions()` → `AccountRepository.reactivateExpiredSuspensions(now)`. Until a run happens an expired suspension still blocks, so the lag is ≤ one interval. Call it through the service bean, not `this`, so `@CacheEvict` applies.
- **Cache**: all four service mutations carry `@CacheEvict(ACCOUNT_SEARCH_CACHE, allEntries = true)` because `AccountStatusView` shows status + the suspension fields.
- **BFF**: `AccountOverviewResponse` and the home rows (`PortalAccountSummary`) expose `suspended` and `suspendedUntil` (never the notes). `home` merges the newest ACTIVE and SUSPENDED accounts (two cached searches, since the search takes one status) and returns both totals. The portal can withdraw/deposit/close through `PortalController` (no suspend/update/reactivate: staff-only); `PortalOrchestrationService` calls `ClientAccountService` and then rebuilds the overview. `PortalCorsConfig` allows only GET/POST/OPTIONS now (PATCH was only used for the removed suspension update).
- **Seed data**: `AccountStatusDemoSeeder` (idempotent *per account number*, not "if empty", so an existing DB with the 52 base accounts still gets the 40; it injects `AccountDataSeeder` purely to force init order) seeds 20 CLOSED (`CH-0000030001..30010`, `SV-0000040001..40010`, created 26–40 months ago, so outside the default 18-month window: use `months=48`) and 20 SUSPENDED (`CH-0000050001..50010`, `SV-0000060001..60010`, created 4–14 months ago; 14 end 3–60 days ahead, 6 indefinite, none pre-expired so the job leaves them alone). Seed dates stay relative (`LocalDate.now().minusMonths(n)` / `LocalDateTime.now()`). Mirror: `db/data/05_seed_closed_and_suspended_accounts.sql`.
- **Database migration gotcha**: `ddl-auto: update` adds the new columns but **never alters an existing enum column**, so a database created before this feature keeps `account_status enum('ACTIVE','CLOSED')` and writing `SUSPENDED` fails. Run `db/ddl/03_account_suspension_migration.sql` (idempotent: it only adds what's missing, so it works whether or not the app has already started on the new version; until then `AccountStatusDemoSeeder` stops at its first suspended account). Adding any future `AccountStatus` value needs the same kind of `ALTER ... MODIFY COLUMN account_status enum(...)` migration plus an update of `db/ddl/01_create_tables.sql`. The hand-run DDL gives `suspended` a `DEFAULT b'0'` (Hibernate emits none) so scripts that omit it stay valid.
- **Hand-run SQL**: `db/dml/04_account_suspension.sql` mirrors suspend/update/reactivate/expire; `db/dml/01_account_operations.sql` already filters withdraw/deposit on `account_status = 'ACTIVE'`, which excludes suspended accounts.

### Paginated account search is a real Spring Data JPA `Specification` query

`GET /v1/api/accounts` (`ClientAccountController.listAccounts` → `org.brite.banking.service.AccountStatusStatementService.listAccountStatuses` → `AccountRepository.search`) retrieves accounts filtered by an optional `accountNumber`/`status`/`createdFrom`/`createdTo`/`closedFrom`/`closedTo` and paginated via a standard Spring `Pageable` (`page`/`size`/`sort` request params, auto-resolved since spring-data-commons is on the classpath — no extra config needed). `accountNumber` implements the "single account vs. all accounts" conditional lookup: it's just another AND'd `Specification` predicate (case-insensitive equality on the `AccountEntity.accountNumber` column) rather than a separate code path, so a provided-but-out-of-date-range account number still yields an empty page instead of bypassing the other filters — there's exactly one query method and one response shape (`Page<AccountStatusView>`) for both "one account" and "all accounts" callers. `AccountRepository.search()` builds a `Specification<AccountEntity>` from whichever filters are non-null and calls `accountJpaRepository.findAll(spec, pageable)` — filtering, sorting, and pagination all happen as real SQL against the database (Caffeine-cached for 10 minutes, see below), not in application code. Only `createdDate`, `closedDate`, `accountStatus`, and `accountNumber` are valid `sort` properties (`AccountRepository.validateSortProperty`, checked *before* calling `findAll` so an invalid property throws the app's own `IllegalArgumentException`/`400` rather than a raw Hibernate property-resolution exception) — anything else throws. Note `checkingAccountNumber`/`savingAccountNumber` were valid sort keys in the old in-memory version but no longer exist as separate concepts now that `AccountEntity` has a single `accountNumber` column; if you're looking at old docs/code referencing those two, they're stale.

The "pull accounts with their status" business logic — date-range validation plus mapping each `Account` to the flattened `org.brite.banking.domain.AccountStatusView` (single `accountNumber`, `accountType`, `accountStatus`, `createdDate`, `closedDate`, `firstName`, `lastName`) — lives in `org.brite.banking.service.AccountStatusStatementService`, deliberately separate from `ClientAccountService`/`AccountRepository`: `AccountRepository.search()` stays a pure data-access concern returning full `Account` entities, and `AccountStatusStatementService` owns the view/projection concern on top of it (`Page<Account>.map(...)` → `Page<AccountStatusView>`). There is deliberately no separate single-account-by-path endpoint (e.g. `GET /v1/api/accounts/{accountNumber}/status`) — it was added and then removed once the `accountNumber` query param on the search endpoint made it redundant; don't re-add it without checking with the user, since `?accountNumber=X` is the one-and-only way to fetch a single account's status/details now. If you need another account-status-derived view or report, add it to `AccountStatusStatementService`. This endpoint sits under `/v1/api/accounts`, so it's covered by the banking rate-limit gateway (see below) like every other banking endpoint.

**Default `months` lookback**: `listAccountStatuses` also takes an optional `months` (Integer). If neither `createdFrom` nor `createdTo` is given, it defaults the range to `[today.minusMonths(months), today]`, falling back to `AccountStatusStatementService.DEFAULT_LOOKBACK_MONTHS` (18) when `months` is also omitted — i.e. the endpoint's baseline behavior is "accounts created in roughly the last year and a half," not "all accounts ever." Supplying either explicit `createdFrom`/`createdTo` bound skips this default entirely and `months` is silently ignored (explicit dates always win); `months <= 0` throws `IllegalArgumentException` (`400`) regardless of whether it would've been used.

**Seed data dates are relative to `LocalDate.now()`, not fixed calendar dates** (see `AccountDataSeeder`) — this was a deliberate fix after the `months` default above initially shipped against fixed 2019-2022 seed dates, which made `GET /v1/api/accounts` return an empty page by default regardless of when the app was started. The "plain" ACTIVE seed accounts (`CH-0000088291`, `SV-0000044102`, and the `seedChecking`/`seedSavings` no-status overloads, 46 accounts total) are seeded 2-5 months back, so they always fall inside the default 18-month window and even a `months=6` query. The two `CLOSED` demo accounts (`CH-0000010004`, `SV-0000020004`) are deliberately seeded 24-30 months back — outside the default window on purpose, to demonstrate that older/closed accounts need a wider `months` (e.g. `months=36`) or an explicit `createdFrom` to surface. If you add new seed accounts, use `LocalDate.now().minusMonths(N)` rather than a fixed `LocalDate.of(...)`, or they'll silently age out of the default window over time.

**Naming note:** despite the "statement" name and the fact that these classes started life in an `org.brite.banking.statement` package, `AccountStatusStatementService` and `AccountStatusView` were later moved to `org.brite.banking.service` and `org.brite.banking.domain` respectively (to match this module's usual controller→service→repository/domain layout) — but the test class `AccountStatusStatementServiceTest` still physically lives under `src/test/java/org/brite/banking/statement/` with `package org.brite.banking.statement;`. This mismatch between the test's package/directory and the production classes' packages is intentional-but-inconsistent leftover state; it compiles fine (javac doesn't require package-to-directory matching), so don't "fix" it by moving things back without checking with the user first.

### Centralized messages and scoped exception handling

All banking exception messages *and* Slf4j log templates live in `BankingMessages` (`org.brite.banking.messages`) as `String.format`/`{}`-style constants — grep there before adding a new error/log string in the banking module. `BankingExceptionHandler` is a `@RestControllerAdvice(basePackages = "org.brite.banking")`, so it only intercepts exceptions thrown from banking controllers; `retail` and `events` controllers catch and translate their own errors inline (see `EventController.receiveEvent`'s try/catch mapping `JsonProcessingException` → 400, everything else → 500).

### Banking API gateway / rate limiter runs as a `Filter`, not through controllers

`org.brite.banking.gateway` implements a lightweight API-gateway ingress layer in front of *every* banking controller path (`/v1/api/accounts/*`, `/v1/api/locations`, `/v1/api/locations/*`, `/v1/client/*`, `/v1/payment/*`, `/notify`, `/notify-sms`, `/report`, `/bff/v1/portal/*`, `/v1/api/staff/*`, `/v1/api/customers/*` — see `BankingGatewayConfig.BANKING_URL_PATTERNS`, shared by all three filters below). None of the filters is a `@Component` — annotating one directly would make Spring Boot also auto-register it for `/*` — so each is registered via its own `FilterRegistrationBean` in `BankingGatewayConfig`. If you add a new banking controller or endpoint, add its path to `BANKING_URL_PATTERNS` or it won't get a `btid`/won't be rate-limited.

Filters run in a fixed order (`BusinessTransactionIdFilter` at `Ordered.HIGHEST_PRECEDENCE`, `BankingRateLimitFilter` at `HIGHEST_PRECEDENCE + 1`, then — staff paths only — `StaffAuthenticationFilter` at `+ 2` (see "Staff endpoints require the employee token"), and `BankingRequestLoggingFilter` at `HIGHEST_PRECEDENCE + 3` — lower value runs first; the three numbered below apply to every banking path):

1. **`BusinessTransactionIdFilter`** generates a `UUID` "btid" for every request, puts it in SLF4J MDC under key `"btid"`, echoes it as the `X-BTID` response header, and clears it in a `finally` block (MDC is thread-local; Tomcat reuses worker threads, so leaving a stale value would bleed into an unrelated later request on that thread). Runs *first* specifically so `BankingRateLimitFilter`'s own rejection logs also carry a `btid`. The `logging.pattern.console` entry in `application.yml` includes `[btid=%X{btid:--}]`, so **every log line in every layer** (controller, service, repository — via SLF4J/MDC propagation, not a threaded parameter) automatically shows the same id for one request; non-request logs (startup, scheduled tasks) show `[btid=-]`.
2. **`BankingRateLimitFilter`** runs before `DispatcherServlet`, so it writes the HTTP response itself (`response.setStatus(...)` + plain-text body) rather than throwing — `BankingExceptionHandler` never sees a rejected request, since `@RestControllerAdvice` only intercepts exceptions from within controller method execution. Two checks, in order: (1) the request must carry the `banking.rate-limit.customer-header-name` header (default `X-Customer-Id`) → `400` if missing/blank; (2) that customer ID is capped at `banking.rate-limit.requests-per-day` (default 1000) requests/day, tracked in `CustomerRateLimiter`'s in-memory `ConcurrentHashMap<customerId, AtomicInteger>` with a single shared day-rollover check (same pattern as `NotificationService`'s SMS daily limit) → `429` once exhausted. Every response gets `X-RateLimit-Limit`/`X-RateLimit-Remaining` headers. `banking.rate-limit.enabled: false` disables just this filter (btid stamping still happens).
3. **`BankingRequestLoggingFilter`** (extends Spring's `AbstractRequestLoggingFilter`) logs every request that gets past the rate limiter — `Request <METHOD> <uri?query>, payload=<body>` at INFO, tagged with the btid — so requests the limiter rejects (missing header / `429`) are *not* body-logged (the rate limiter logs those itself). The body only exists in the cached wrapper once a controller has read it, so the line is written **after** the chain runs (`afterRequest`; `beforeRequest` is a deliberate no-op) — it still appears if the controller rejects the request. Payload is truncated to `banking.request-logging.max-payload-length` (default 2000); `dateOfBirth`, `phoneNumber` and `password` values are masked to `***` (`BankingRequestLoggingFilter.mask`) — if a new request field is more sensitive than names/addresses, mask it there too. Headers are never logged. `banking.request-logging.enabled: false` removes the filter bean entirely (`@ConditionalOnProperty` on its bean method; default on). The message text already contains the HTTP method, so the template (`BankingMessages.LOG_REQUEST_RECEIVED`) doesn't add one.

### Notification gating

`NotificationService.sendEmail`/`sendSms` are `@Async` fire-and-forget methods gated by the bound `BriteEmailConfigValues`/`BriteSmsNotificationConfigValues` (`notification.email.*` / `notification.sms.*` in `application.yml`). SMS additionally enforces `dailyLimit` via an in-memory day-rolling counter in `NotificationService`. Both are invoked from `ClientAccountService` (register, withdraw) and `BankStatementService` (statement generation) — deposit does not currently trigger a notification.

### Resilience4j annotation ordering

`PaymentService.processPayment` stacks `@Retry` above `@CircuitBreaker` deliberately (see the comment on that method): Retry is the outer aspect so each retry attempt still respects the breaker's state, and only `@Retry` declares a `fallbackMethod` — if `@CircuitBreaker` also had one, it would swallow failures before `@Retry` ever saw them.

### Liveness/readiness probes

`management.endpoint.health.probes.enabled: true` (in `application.yml`) turns on Spring Boot's Kubernetes-style health groups, exposed at `/actuator/health/liveness` and `/actuator/health/readiness`. Liveness only reflects `LivenessStateHealthIndicator` (the JVM process), so it stays `UP` even if MySQL is down. Readiness is explicitly configured (`management.endpoint.health.group.readiness.include: readinessState,db`) to also fold in the `DataSourceHealthIndicator`, so it flips to `DOWN` if the MySQL connection is lost — that's deliberate, since this app can't actually serve most endpoints without the datasource. If you add other hard dependencies (e.g. a new external service health indicator), add them to that same `readiness.include` list rather than relying on the default `/actuator/health` aggregate.

### App-wide execution-time logging via Spring AOP

`org.brite.common.logging.ExecutionTimeLoggingAspect` is a Spring AOP `@Aspect`/`@Around` advice with pointcut `within(@org.springframework.web.bind.annotation.RestController *)` — it wraps *every* `@RestController` method in the app (banking, sample; not just one module) in a `System.nanoTime()` timer and logs `"<ClassName>.<method>(..) executed in <N> ms"` at INFO, using try/finally so failed requests still get logged. Requires `spring-boot-starter-aop` (pulls in AspectJ weaver) — added specifically for this, since nothing else in the app used Spring AOP directly before (Resilience4j's `@CircuitBreaker`/`@Retry` are also AOP-based, but that starter brought its own aspect support). If you add a new controller anywhere under `org.brite`, it's automatically covered — no per-controller change needed. Don't confuse this with `AccountStatusStatementService.listAccountStatuses`'s own `log.debug` calls — those are business-level logging, this aspect is purely infrastructure/observability at the HTTP-method-call boundary.

### Account search results are cached for 10 minutes (Caffeine)

`AccountStatusStatementService.listAccountStatuses` (backing `GET /v1/api/accounts`) is `@Cacheable(cacheNames = AccountStatusStatementService.ACCOUNT_SEARCH_CACHE)` — the cache name is a public constant (`"accountSearch"`) shared with the evicting side. TTL is configured once, in `application.yml`, as `spring.cache.caffeine.spec: expireAfterWrite=10m` (Caffeine's cache manager is auto-configured by Spring Boot since `caffeine` is on the classpath and `spring.cache.type: caffeine`); there's no per-annotation TTL — `spring-boot-starter-cache`'s default `ConcurrentMapCacheManager` doesn't support TTL at all, which is why Caffeine was added as a dependency specifically for this. `@EnableCaching` lives on `BankingServicesApplication`.

This is safe to cache because `AccountStatusView` never exposes balance — only `accountNumber`, `accountType`, `accountStatus`, `createdDate`, `closedDate`, `firstName`, `lastName`, none of which withdraw/deposit ever change. The mutations that *do* change a field this view shows are `ClientAccountService.registerNewClientAccount` (a new account appears), `.closeAccount`/`.closeAccounts` (`accountStatus`/`closedDate` change) and every `AccountSuspensionService` mutation (status and the suspension fields change) — all carry `@CacheEvict(cacheNames = AccountStatusStatementService.ACCOUNT_SEARCH_CACHE, allEntries = true)`. If you add another account mutation that changes a field in `AccountStatusView`, evict this same cache from it; if you cache anything that *does* expose balance (e.g. the full `Account`), you must evict on withdraw/deposit too, or callers will read stale balances for up to 10 minutes.

### Banking OpenAPI spec is hand-written and served statically (not generated)

`src/main/resources/static/openapi/banking-openapi.yaml` (OpenAPI 3.0.3) documents every banking endpoint (`/v1/api/accounts/**`, `/v1/api/locations/**`, `/v1/client/name`, `/v1/payment/process`, `/notify`, `/notify-sms`, `/report`, and the staff/login endpoints under tags `Staff` and `Login`, with the `EmployeeNumber` apiKey scheme). **It is not generated from the code** — there's no springdoc, so it won't notice when a controller, DTO, validation rule, or exception mapping changes. If you change any of those in the banking module, update the spec in the same change (request/response schemas, `required` lists, status codes, and the plain-text-vs-JSON error split below). Validate edits with `openapi-spec-validator` (`pip install openapi-spec-validator`); it only checks structure, not that the spec still matches the controllers.

Things the spec encodes that are easy to get wrong when editing it: business-rule failures from `BankingExceptionHandler` and the gateway filters are `text/plain`, while `@Valid` body failures fall through to Spring Boot's default JSON error (`SpringErrorResponse`); `X-Customer-Id` is modeled as an `apiKey` security scheme but is only a rate-limit key, not authentication (staff endpoints use the `BearerAuth` http/JWT scheme and every one lists a `401`; keep the `EmployeeRole`/`EmployeePrivilege`/`LoginStatus` enums equal to the Java enums); `Account` populates only the checking-or-saving field pair matching `accountType`; `Customer` responses include a derived `dateOfBirthValid` (Jackson serializing `isDateOfBirthValid()`); `WithdrawalRequest.withdrawalDate`/`withdrawalStatus` are accepted but ignored; dates in requests use `MM/dd/yyyy` for `dateOfBirth` but ISO `yyyy-MM-dd` everywhere else. In YAML flow sequences, quote strings containing `,` (e.g. `['createdDate,desc']`) or they split into separate items, and quote plain scalars containing `: `.

Swagger UI is the `org.webjars:swagger-ui` webjar plus `webjars-locator-lite` (so asset URLs need no version) and a static page, `static/swagger-ui/index.html`, which loads the spec by relative URL so it works under the `/brite` context path: `http://localhost:8081/brite/swagger-ui/index.html`, spec at `/brite/openapi/banking-openapi.yaml`. Those static paths aren't in `BankingGatewayConfig.BANKING_URL_PATTERNS`, so loading the UI needs no `X-Customer-Id`; its "Try it out" calls do, via the Authorize button.

### `db/` holds hand-runnable SQL (DDL, seed data, DML) that mirrors the entities and seeder

`db/ddl/01_create_tables.sql` is the schema Hibernate 6.6's `MySQLDialect` generates from the JPA entities (banking only; the `events` table is eventservice's), so it matches what `ddl-auto: update` builds on a fresh database — including Hibernate's own FK constraint names, deliberately kept so a later `update` finds nothing to change. `db/data/01_seed_customers_accounts.sql` was *generated by parsing* `AccountDataSeeder` (same 52 accounts, dates as `DATE_SUB(CURDATE(), INTERVAL n MONTH)` to stay relative like `LocalDate.now()`); `db/data/05_...` mirrors `AccountStatusDemoSeeder`'s 40 closed/suspended accounts, and `db/ddl/03_account_suspension_migration.sql` upgrades an older database; `db/data/07`-`09` mirror the employee and login seeders and `db/ddl/04`-`06` are the idempotent migrations for new columns (customer phone, transaction handler, login status). `db/dml/03_reset_banking_data.sql` also clears the employee and login tables, because logins reference customers/employees by id and ids restart at 1. `db/dml/` has the writes/queries as plain SQL, and `db/README.md` lists every file. **None of this is executed by the app** — nothing to keep in sync automatically — so when you add/rename/retype a column on an entity, or change `AccountDataSeeder`'s accounts, update the matching `db/` scripts in the same change. To regenerate the DDL without a database connection, boot Hibernate with `jakarta.persistence.schema-generation.scripts.action=create` + `hibernate.boot.allow_jdbc_metadata_access=false` (Hibernate 6.6 moved `SchemaExport` out of hibernate-core, so the JPA script properties are the easy route); Boot 3.4's physical naming strategy is Hibernate's `CamelCaseToUnderscoresNamingStrategy`. The DML scripts were reviewed but not executed (they use MySQL session variables and `SELECT ... INTO @var`); the DDL and `data/` scripts were verified by loading them into H2 in MySQL mode.

## Testing

Most existing tests use `@SpringBootTest` + `MockMvc` (see `BankingServicesApplicationTests`). Because the full context boots, those tests need MySQL reachable as described above — and, since the banking JPA migration, so does `AccountDataSeeder`'s `@PostConstruct` seeding, which runs as part of that same context boot (you'll see "Seeding demo banking accounts" or "Accounts table already has data" in these tests' output too).

`ClientAccountServiceTest`, `AccountStatusStatementServiceTest`, `CustomerRateLimiterTest`, `BankingRateLimitFilterTest`, `BusinessTransactionIdFilterTest`, and `BankingRequestLoggingFilterTest` (`src/test/java/org/brite/banking/...`) are deliberately plain JUnit 5 + Mockito unit tests with **no** `@SpringBootTest` — none of `ClientAccountService`'s mocked collaborators, `AccountStatusStatementService`, `CustomerRateLimiter`, `BankingRateLimitFilter`, `BusinessTransactionIdFilter`, or `BankingRequestLoggingFilter` have Spring/MySQL dependencies of their own (mocked repository facades, in-memory counters, plain-POJO collaborators, mocked `HttpServletRequest`/`Response`/`FilterChain`, direct `MDC` reads), so these run standalone even without MySQL up. (`BankingRequestLoggingFilterTest` is the one that doesn't use Mockito: it drives the filter with `MockHttpServletRequest` and a stand-in chain that reads the body, then asserts on log output via a Logback `ListAppender` attached to the filter's logger.) When adding tests for banking business logic (validation rules, status transitions, balance math, rate limiting), prefer this pattern - mock `AccountRepository`/`TransactionRepository`/`WithdrawalRepository` rather than instantiating them, since they're JPA-backed now and need a real `AccountJpaRepository`/etc. - over booting the full context; reserve `@SpringBootTest`/`MockMvc` for controller-layer/wiring tests.

**`AccountRepositoryTest` is the one exception**: since `AccountRepository.search()` now builds a real `Specification` query, a Mockito-mocked `AccountJpaRepository` could only assert "was `findAll(spec, pageable)` called," not that the resulting SQL/filtering is actually correct - that needs a real database. It's a `@DataJpaTest` (`@ContextConfiguration(classes = BankingServicesApplication.class)` + `@TestPropertySource` clearing `spring.jpa.properties.hibernate.dialect` and forcing `ddl-auto=create-drop`, since `application.yml` hardcodes the MySQL dialect and `@DataJpaTest`'s embedded-H2 swap only replaces the datasource, not that dialect override) using the embedded H2 dependency instead of live MySQL - each test runs in a rolled-back transaction against a fresh schema. `AccountRepository` itself is a plain `@Repository` class, not a Spring Data interface, so it's constructed directly in `@BeforeEach` around the real `@Autowired AccountJpaRepository`, rather than relying on `@DataJpaTest`'s component scan (which only auto-creates entities/Spring Data repository beans) to provide it.

`ExecutionTimeLoggingAspectTest` (`org.brite.common.logging`) and `AccountSearchCachingTest` (`org.brite.banking.service`) follow the same no-Spring-context pattern for the AOP/caching additions above: the former calls `ExecutionTimeLoggingAspect.logExecutionTime(...)` directly against a mocked `ProceedingJoinPoint` rather than verifying the AspectJ pointcut actually weaves (that's a Spring/classpath-wiring concern, not business logic); the latter uses plain reflection to assert `@Cacheable`/`@CacheEvict` are present and reference the same cache name, since actually exercising cache population/eviction/TTL requires a live `ApplicationContext` with the proxy applied — the `BankingServicesApplicationTests`/`@SpringBootTest` suite exercises the real thing incidentally (its MockMvc calls flow through the aspect, which is why its test output shows `ExecutionTimeLoggingAspect` log lines).

Suspension tests follow the same split: `AccountSuspensionServiceTest`/`AccountSuspensionExpiryJobTest` are plain Mockito unit tests (time-window rules, partial update, expiry hook); `StaffSuspensionControllerTest` is standalone MockMvc (the staff suspend/update/reactivate endpoints; the customer routes no longer exist) (no Spring context, no MySQL) with the real `BankingExceptionHandler`; the state rules (suspended blocks withdraw/deposit, reactivate, expiry query, close-from-suspended) are in `AccountRepositoryTest` against H2 because they're real SQL; `AccountStatusDemoSeederTest` runs both seeders on H2 through a minimal `@Import` context (beans imported that way get their class name as bean name, which is why the seeder depends on the base seeder by constructor injection, not `@DependsOn("accountDataSeeder")`).

Employee and login tests: `EmployeeServiceTest`/`EmployeeCredentialServiceTest`/`CustomerCredentialServiceTest` are plain Mockito units (real `BCryptPasswordEncoder(4)` for speed); `StaffControllerTest`/`LoginControllerTest` are standalone MockMvc with the real `BankingExceptionHandler` (`StaffControllerTest` uses the real `EmployeeService`/`StaffAccountService`/`StaffLoginService` over mocked repositories, so the privilege rules are exercised end to end up to the account services); `EmployeeCredentialPersistenceTest`/`CustomerCredentialPersistenceTest`/`EmployeeDataSeederTest` run the real seeders, facades and services on H2 through a minimal `@Import` context, and the credential ones are `@Transactional(propagation = NOT_SUPPORTED)` so the service's own commits (including the failed-attempt count saved while `verify` throws) are what is observed — each test uses a different seeded user because the data is shared. `BankingRequestLoggingFilterTest` also covers password masking.

`JwtServiceTest` is a plain unit test using a fixed `Clock` (package-private constructor) so expiry needs no sleeping; it covers tampering, foreign keys/issuers, `alg: none` and unknown token types. `LoginControllerTest` builds the real `LoginService` + `JwtService` over mocked credential services and checks that the returned token parses to the right principal and that failures return no token.
